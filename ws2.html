How the token travels

docker build . --tag ws2
docker run -it ws2                         # env shows no token
docker run -it --env-file mytoken.txt ws2  # env now shows CSC_519_GITHUB_TOKEN
docker run --env-file mytoken.txt ws2      # no -it: just run the CMD program and exit

Environment variables

A terminal is a computational context where you can declare variables, like in any program. Environment variables are name=value strings that a process inherits from whatever started it. They are the standard way to hand configuration to a program without editing the program.

You typeMeaning
envPrint every environment variable in this shell (HOSTNAME, HOME, PATH, PWD…)
export NAME=valueDefine a variable and pass it to child processes
$NAMERead it in the shell, e.g. curl -H "Authorization: Bearer $NCSU_GITHUB_TOKEN" …
NAME=value lines in a fileThe X=Y format --env-file expects. Left side is the variable name seen inside the container
os.environ.get('NAME')Read it from Python (needs import os). Returns None if unset
process.env.NAMERead it from Node.js (used in WS5 for DB_HOST, PORT)

The same idea shows up all semester: ${{ secrets.X }} in GitHub Actions, Environment=DB_HOST=… in a systemd unit, PATH deciding which program a command name finds.

Exam angleWhy use an environment variable? Because it separates configuration from code: the same image runs in dev, test and prod with different values, and a secret never has to be written into source or into the image.

Secrets and the principle of least privilege

A personal access token (PAT) is a secret: a string that lets a program act as you on the GitHub API. Treat it like a password.

  • Never commit a token. Put the token file in .gitignore. Bots scan GitHub for leaked credentials and exploit them within minutes; the workshop penalty (and getting fired in industry) reflects that.
  • Never bake a token into an image. An image is a binary artifact that gets shared. Anyone who can read it can extract the token (image inspection tools, reverse engineering).
  • Least privilege. Grant only the access the task needs: scope the PAT to repo on one repository, and give it an expiry date.
  • Passing configuration (owner, repo name) as environment variables or arguments is better than hard-coding it too.

The Workshop 2 Dockerfile

FROM alpine:latest                    # bare-bones base: no python
COPY my-program.py /home              # put the program into the image
USER root
WORKDIR /home
RUN apk --update-cache add python3    # build time: install python into a layer
#CMD ["/bin/sh"]                      # old default: interactive shell
CMD python /home/my-program.py        # run time: start the program
  • Each instruction creates a new layer in the image.
  • Installing Python by hand in a running container (apk add python3) works once. Putting it in a RUN line makes it part of every container.
  • Alternative base python:3.12-alpine: less work, but now you depend on someone else's image on Docker Hub. Make that choice knowingly.
  • The token is absent on purpose. No ENV TOKEN=…, no COPY mytoken.txt.

REST APIs

An API answers "how can my software talk to other software?". REST (Representational State Transfer, Roy Fielding's 2000 thesis) is an architectural style: resources are nouns in the URL, HTTP verbs are the operations, and data travels as JSON.

VerbActionExampleIdempotent?
GETReadGET /repos/{owner}/{repo}/branches lists branchesYes (and safe)
POSTCreatePOST /repos/{owner}/{repo}/git/refs creates a branchNo
PUTUpdate / replacePUT /recipes/3Yes
DELETEDeleteDELETE /recipes/1Yes

Status codes

  • 200 OK, 201 Created: it worked
  • 4xx the client did something wrong: 400 bad request, 401 bad credentials, 404 not found, 422 validation failed (branch already exists)
  • 500 the server did something wrong

Constraints and design rules

  • Client-server, stateless, cacheable, layered, uniform interface
  • Collections /dogs, elements /dogs/1234, associations /owners/5678/dogs
  • Filters go after the ?: /dogs?color=red
  • Version the API; paginate; use standard auth (OAuth)
Test your token from a shell
curl -H "Authorization: Bearer $CSC_519_GITHUB_TOKEN" https://api.github.com/users/UNITY_ID_ncstate
# -H adds a request header. Success returns JSON; an expired token returns "Bad credentials".
API design principles quoted in lecture: do one thing well; you can never remove a public API (Hyrum's Law); names matter; don't leak implementation details; don't make the client do what the API could do.

The branch-creating program

Requirements: run in Alpine, read the token from an environment variable, create dev and release, and gracefully handle the case that they already exist. A branch is just a named pointer (a "ref") to a commit, so creating one means "create ref refs/heads/dev pointing at main's latest commit SHA".

Pseudocode (what your my-program.py does)
token = env["CSC_519_GITHUB_TOKEN"]
if token is missing: print error, exit 1

sha = GET /repos/OWNER/REPO/git/ref/heads/main
        -> object.sha

for name in ["dev", "release"]:
    status = POST /repos/OWNER/REPO/git/refs
             body {ref: "refs/heads/"+name, sha: sha}
             header Authorization: Bearer token
    if status == 201: print "created"
    elif status == 422: print "already exists, skipping"
    else: raise error
Same thing with PyGithub
import os
from github import Github, GithubException

g = Github(os.environ["CSC_519_GITHUB_TOKEN"])
repo = g.get_repo("OWNER/REPO")
sha = repo.get_branch("main").commit.sha

for name in ("dev", "release"):
    try:
        repo.create_git_ref(
            ref=f"refs/heads/{name}", sha=sha)
    except GithubException as e:
        if e.status != 422:   # 422 = exists
            raise
Exam angleThe "already exists" check is what makes the program safe to run twice with the same end result. That is idempotence, achieved by hand. POST is not idempotent on its own, so the program has to check. Ansible modules do this checking for you (Workshop 4). Also notice the program prints the token's length, not the token: never echo secrets into logs.

Git Flow and branch-based development

The dev and release branches you created are two of the Git Flow lanes. The slide was marked "important".

BranchBranched fromMerges intoRules from the slides
mainStays clean. Don't break the build. Build from main. Use release tags. Quality gates protect main
developmainreleaseIntegration branch. "Dev might at times be broken"
featuredevelopdevelop (via PR)Name it unity_id__description. Don't squash commits (at first)
releasedevelopmain (tagged) and developStabilize a version before it ships
hotfixmainmain and developUrgent production fix that skips the normal path
Exam angleThis exact question was shown in class as a sample: "In a git flow paradigm, a feature branch is branched from main." False: change main to develop. Also know the "special moments": main has two inbound edges (release, hotfix); develop receives features plus the merge-backs from hotfix and release.

Branch-based development in general: nobody commits straight to the shared branch. Work happens on a short-lived branch, and the only way in is a reviewed merge. GitHub Actions (WS3) attaches automation to these same edges.

Pull requests, Modern Code Review, and diff time

Pull request (PR)
A request to merge one branch into another. It can contain one or more commits, shows the diff, hosts discussion, and is where automated checks report.
Diff time
The critical moment in the process when a code change is proposed. It is when peer review happens and, increasingly, when static analysis runs ("Scaling static analyses at Facebook", 2019).
Modern Code Review
Lightweight, tool-based, asynchronous peer review of a diff before merge, as opposed to formal inspection meetings ("Modern code review: a case study at Google", 2018).
Continuous Integration (CI)
Frequently putting everyone's changes together. Smaller changes are easier to debug. Aim for the "Goldilocks" granularity: not too big, not too small.

Workshop 2 also asked for two professional habits: meaningful commit messages and developing through pull requests even when working alone.

Practice

The exam has three question types: true / false with corrections, matching concepts, and naming the tool from a code snippet. "Self-check" and "Read the code" items are for understanding only. On true / false, underline the wrong word and write the fix; a plain "not" earns nothing.
True / FalseIn a git flow paradigm, a feature branch is branched from main.
False. Change main to develop. (Sample question from the lecture slides.)
True / FalseIn Git Flow, a hotfix branch is merged only into main.
False. Change only into main to into main and develop, so the fix is not lost in the next release.
True / FalseThe safest place to store an API token is in the Dockerfile with an ENV instruction.
False. That bakes the secret into the image. Pass it at run time (--env-file) or, better, use a secrets manager.
True / FalseThe principle of least privilege says a token should be given the broadest scope so that automation never fails.
False. Change broadest to narrowest (only what the task requires), and give it an expiry.
True / False"Diff time" is the moment when code review and, increasingly, static analysis happen.
True. It is a discrete event in the process, typically the pull request.
True / FalseREST APIs typically consume and produce XML and use the verbs OPEN, READ, WRITE, CLOSE.
False. They typically use JSON and the HTTP verbs GET, POST, PUT, DELETE.
True / FalseAn HTTP 500 status code means the client sent a bad request.
False. Change 500 to 400 (or: 500 means the server failed).
True / Falsedocker run --env-file mytoken.txt ws2 stores the token permanently inside the ws2 image.
False. It sets an environment variable in that one container at run time. The image is unchanged.
Self-checkWhy is passing a token as an environment variable better than hard-coding it, and what is better still?
Hard-coding puts the secret into source control and into the image, where anyone with access can read it and where it is hard to rotate. An env var keeps it out of both and lets the same image run with different credentials. Better still is a secrets manager (GitHub repository secrets, podman secrets), which stores it encrypted and controls access.
Self-checkWhat does .gitignore containing mytoken.txt accomplish, and what does it not protect against?
Git will not track or commit that file, so it cannot be pushed by accident. It does not protect a token that is pasted into code, printed in logs or screenshots, or baked into an image.
Read the codeYour program gets HTTP 422 from POST /repos/…/git/refs on its second run. What happened and what should the program do?
The branch already exists (validation failed). The program should treat that as success: report "already exists" and continue, so that running it any number of times leaves the repo in the same state.
Self-checkName the two branches whose commits can merge into main in Git Flow, and say why direct feature merges to main are avoided.
Release and hotfix. Main must stay clean and buildable because releases are built from it; features integrate and get tested on develop first, behind quality gates.
Self-checkIn one sentence each, define pull request and Modern Code Review.
A pull request proposes merging one branch into another and is where the diff is discussed and checked. Modern Code Review is lightweight, tool-supported peer review of that diff before it merges.
