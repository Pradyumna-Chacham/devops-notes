Vocabulary: how the pieces nest

TermMeaning
WorkflowYAML file (.yml or .yaml) in .github/workflows/. A repo with a non-empty folder there is using Actions
EventSomething that happens in the repo (push, PR opened, issue created, a schedule). The on: key says which events start the workflow
JobA named unit of work. Each job runs on one runner, in its own clean environment
StepOne command (run:) or one reusable action (uses:) inside a job
RunnerThe compute that executes jobs. GitHub-hosted (their headless VMs) or self-hosted (your VM)
ContextVariables GitHub provides at run time, read with ${{ … }}
SecretEncrypted value stored in the repo settings, read with ${{ secrets.NAME }}

YAML has a one-to-one correspondence with JSON: any workflow can be converted to JSON and back. Indentation is the structure.

hello-world, line by line

LineWhat it means
name: hello-worldLabel shown in the Actions tab. Optional, but good names matter
on: pushRequired and critical. Run this workflow in response to push events. Actions is an event-driven architecture
jobs:Start of the list of jobs (one here)
  this-is-a-job-name:The job's identifier (required)
    runs-on: self-hostedWhich compute handles the job: your own machine, not GitHub's
    steps:The ordered sequence of commands
      - run: exit 0run: prefixes a shell command. exit 0 returns Unix return code 0, forcing success
Exam angleReturn codes decide pass or fail. exit 0 means success and the run goes green. Any non-zero code (exit 1) fails the step, the job and the workflow run. This is how a failing test suite blocks a pipeline: the test command exits non-zero. That mechanism is a quality gate.

Events: the "on" that drives everything

Starter: every push
on: push
Deliverable: PR opened or reopened
on:
  pull_request:
    types: [opened, reopened]
Other triggers worth knowing
on:
  push:
    branches: [main]      # only pushes to main
  schedule:
    - cron: "0 6 * * *"   # time-based
  workflow_dispatch:      # manual button
  issues:
    types: [opened]

In Git Flow terms, Actions adds automation to the edges of the diagram: run tests when a PR targets develop, build and tag when a release merges to main, label stale issues on a schedule. The form asked you to pick an event and say what you would do in response and why; have one example ready.

EventSensible responseWhy
pull_requestLint, unit tests, static analysisFeedback at diff time, before review and merge
push to mainBuild, package, deploy to stagingMain is always releasable; keep it verified
release publishedDeploy to productionTies deployment to a tagged version
scheduleNightly security scan, close stale issuesSome checks are not tied to a code change

Runners, your VM, and SSH

  • An action runner is compute configured to perform GitHub actions. You registered your persistent VM under Settings → Actions → Runners by pasting GitHub's download and configure commands over an SSH session.
  • The runner program only stays alive while something keeps it running. Closing the SSH session stops it unless you install it as a service (sudo ./svc.sh install, sudo ./svc.sh start) or keep it in screen / tmux.
  • SSH (secure shell) gives you an encrypted terminal on a remote machine. You need a username and the hostname or IP: ssh unityid@hostname.
  • From off campus: use the VPN, or hop through the terminal gateway (remote.eos.ncsu.edu). Do not run programs or runners on the gateway itself.
  • Each job gets its own clean environment on the runner, and steps in one job share a workspace (which is why your second step could cat branches.json written by the first).
GitHub-hosted runnerSelf-hosted runner
Who owns the machineGitHub (fresh headless VM per job)You (on premises or your cloud)
UpsideZero maintenance, always cleanYour hardware, your network access, your tools
DownsideCannot reach private networks; usage limitsYou patch and secure it; state can leak between runs

Contexts and secrets

Anything inside ${{ … }} is an expression evaluated by GitHub when the workflow runs, before the shell sees the command. The github context describes the run; the secrets context exposes repository secrets.

ExpressionBecomes
${{ github.actor }}Username that triggered the run (your Unity ID)
${{ github.repository }}owner/repo-name, so nothing is hard-coded
${{ github.event_name }}push, pull_request, …
${{ github.ref }} / github.shaBranch or tag ref / commit SHA that triggered the run
${{ secrets.NCSU_GITHUB_TOKEN }}The encrypted repository secret, decrypted only for this run and masked in logs
Your Workshop 3 deliverable
name: hello-world
run-name: ${{ github.actor }} is learning       # personalised title for each run
on:
  pull_request:
    types: [opened, reopened]                    # event-driven: PR opened OR reopened
jobs:
  this-is-a-job-name:
    runs-on: self-hosted                         # your VM
    steps:
      - run: |                                   # "|" starts a multi-line shell script
          curl --request GET \
            --url "https://api.github.com/repos/${{ github.repository }}/branches" \
            --header "Authorization: Bearer ${{ secrets.NCSU_GITHUB_TOKEN }}" \
            --output branches.json
      - run: cat branches.json                   # second step, same job, same workspace

No username, repository name or token is typed anywhere. That was the requirement: prove you can pass context variables and a secret through a workflow.

WorkshopWhere the token livedHow the program got it
WS2mytoken.txt on your laptop (gitignored)--env-file → environment variable
WS3GitHub's secrets manager (Settings → Secrets and variables)${{ secrets.NAME }} at run time
Exam angle"Secrets manager" is the improvement over WS2's env file: the value is stored encrypted, is not visible after you save it, is not in the repo or workflow file, and is injected only when the workflow runs. The rule is the same in every workshop: never check in a token.

The DevOps lifecycle

Working definition from lecture: "DevOps is a set of practices designed to help teams build, test, and release software faster and more reliably." It joins Development and Operations, usually drawn as an infinity loop because it never ends.

DevOps is event-driven

  1. Code commit
  2. Pull request to a special branch
  3. Automated testing
  4. Passing tests (a quality gate) can automatically trigger promotion to the next phase, for example staging

Pipelines, stages and hooks

Pipeline (general)
An architectural style for incrementally processing data with independent components or stages. A pipe is a message queue; a filter reads a message from an input pipe, processes it, and writes the result to an output pipe.
DevOps pipeline
Its goal: "apply a series of checks, tests, and transformations onto a unit of change, such that a production environment is safely and reliably changed in a timely manner."
Unit of change
The thing travelling down the pipeline: a commit, a pull request, a build.
Hook
A mechanism for specifying an action that occurs in response to an event. Examples: a git pre-commit hook that runs npm test and cancels the commit on failure; a webhook that notifies another system; on: in a workflow.

Real pipelines are "more complicated": not all changes are correct or safe, and product and infrastructure needs vary. Companies run a federation of hundreds to thousands of loosely aligned pipelines, not one global one. Netflix Spinnaker is the slides' example of a fully automated pipeline: bake immutable VM images, built-in deployment strategies (highlander, red/black), restrict stages to time windows, Chaos Monkey integration, with canary and hotfix stages.

Pipelines outsource the heavy lifting

A pipeline is integrative technology. The real work is done by build and task managers it calls:

ToolConcept to knowExample
makeA target is a group of commands; a source is a dependency of a target, used to infer what must run firstmake publish-latest
Maven (Java, XML)A phase is a stage in the build lifecycle (compile, test, package, verify, deploy); phases contain goals executed by pluginsmvn verify
grunt / npmA task runs a registered plugin or arbitrary JavaScriptnpm run deploy:stage

Continuous integration, delivery and deployment

TermDefinition
Continuous IntegrationDevelopers automatically build, test and analyze a software change in response to every change committed to the source repository
Continuous DeliveryEvery change is carried through testing and staging so it is always ready to release; the final push to production may still be a human decision
Continuous Deployment"A process in which incremental software changes are automatically tested, vetted, and deployed to production environments" (Glossary 1)

Lecture's caveat: "continuous" is imprecise. Code changes arrive at discrete moments (diff time), and production updates happen at intervals.

CI principles

  • Commit code frequently
  • Don't commit broken code
  • Fix broken builds immediately
  • Write automated developer tests
  • All tests and inspections must pass
  • Run private builds
  • Avoid getting broken code

Claimed benefits

  • Detect and fix defects faster
  • Health of the software is measurable
  • Fewer assumptions about the environment
  • Less repetitive manual process
  • Deployable software at any point in time
  • Global feedback about failure gives developers confidence

The problem CI solves: code "that worked individually were put together and the whole usually failed in ways that were infuriatingly difficult to find". Pain points from the studies: "why did the build fail?" and builds that take too long. Some companies use build teams to maintain CI scripts and infrastructure; they can act as gatekeepers on integration. CD pipeline configs have their own "smells", which linters such as CD-Linter detect.

History that could appear as a matching item: XP "integrate often" and the 10-minute build (1999), Fowler's CI post (2000), Jenkins (2005), Travis CI (2011), Spinnaker (2015), Jenkins 2 "pipeline-as-code" (2016), GitOps (2017).

Roles and team size

RoleResponsible for
Service OwnerOutside coordination. Maintains and communicates the vision of the service
GatekeeperDecisions to move to the next stage in the deployment pipeline (decisions might be automated)
Release Engineer / CoordinatorThe entire release process: approving late-breaking additions, the back-out decision, refereeing bug-severity disputes
DevOps EngineerCare and feeding of the tools used throughout the DevOps toolchain
Reliability EngineerThe time period immediately after deployment

The "two large pizzas" rule (Amazon): a development team should be no larger than what two pizzas can feed. It is about team size, and small teams each own one service, exposed over a well-defined interface such as REST APIs. Many independent services make a microservices architecture. Lamport's warning comes with it: "A distributed system is one in which the failure of a computer you didn't even know existed can render your own computer unusable."

Two terms defined in the same lecture: provisioning (creating and preparing machines or environments) and toolchain (the set of tools chained together to move code to production).

Practice

Answer in your head first, then open each one. On the real T/F questions you underline the wrong word and write the fix. A plain "not" earns nothing.
True / FalseThe "two large pizzas" rule states that a DevOps pipeline should take less time to deploy than it takes for the team to eat two large pizzas.
False. Sample question from the slides. The rule is about team size: a team should be no larger than two large pizzas can feed.
True / FalseIn a GitHub Actions workflow, the runs-on: keyword specifies which events trigger the workflow.
False. Change runs-on: to on:. runs-on: picks the runner.
True / FalseGitHub Actions workflows are written in JSON files stored in the .github/actions folder.
False. They are YAML files in .github/workflows. (YAML converts one-to-one to JSON, but the files are YAML.)
True / FalseA step that runs exit 1 causes the workflow run to succeed.
False. Change succeed to fail (or change exit 1 to exit 0). Zero is the success return code.
True / FalseA self-hosted runner is a virtual machine owned and managed by GitHub.
False. Change self-hosted to GitHub-hosted. A self-hosted runner is your own machine.
True / FalseThe Gatekeeper is responsible for the time period immediately after deployment.
False. Change Gatekeeper to Reliability Engineer. The Gatekeeper decides whether a change moves to the next pipeline stage.
True / FalseContinuous Integration is a practice where developers automatically build, test and analyze a change in response to every change committed to the repository.
True. That is the slide definition.
True / FalseA hook is a mechanism for specifying an action that occurs in response to an event.
True. Git pre-commit hooks and webhooks are examples.
True / FalseStaging is the pipeline stage in which unit tests are run against the developer's laptop.
False. Staging (baking) runs system tests in a production-like environment. Unit tests belong to the Test stage.
Read the code--header "Authorization: Bearer ${{ secrets.NCSU_GITHUB_TOKEN }}" Who replaces the ${{ … }} part, when, and why is this safer than typing the token?
GitHub's workflow engine evaluates the expression when the run starts, substituting the decrypted repository secret before the shell command executes. The token never appears in the workflow file or repo, is stored encrypted, and is masked in logs.
Read the codeA workflow has on: push and you want it to run only when a pull request is opened or reopened. What changes?
Replace the trigger with on: → pull_request: → types: [opened, reopened]. Nothing else has to change; the event is the only thing that decides when it runs.
Short answerWhy is DevOps described as "event-driven"? Give the chain of events from the slides.
Automation runs in response to events instead of on someone's manual schedule: a code commit, a pull request to a special branch, automated testing, and passing tests (a quality gate) automatically triggering the next CI/CD phase such as staging.
Short answerState the goal of a DevOps pipeline.
To apply a series of checks, tests and transformations to a unit of change so that the production environment is changed safely, reliably and in a timely manner.
MatchingMatch each to its closest tool: Continuous Integration, Infrastructure as Code, Containerization, Version Control. (Tools: Ansible, Git, GitHub Actions, Docker / Podman.)
Continuous Integration ↔ GitHub Actions. Infrastructure as Code ↔ Ansible. Containerization ↔ Docker / Podman. Version Control ↔ Git. On the slide, Microservices was also in the left column; items "might connect to zero, one, or multiple" on the right, so the closest link for Microservices is Docker / Podman (services packaged as containers), and it is fine to argue for none.
