Deployment rings

Deployment rings (a.k.a. rollout rings) release a change to progressively larger groups of users. Each ring must look healthy before the change is promoted to the next.

RingWhoPurposeCharacter
0: CanariesInternal users, volunteers, a small slice of trafficCatch defects first, at minimum impactMost volatile; sees the largest set of new features
1: Early adoptersUsers who opted in to previewsValidate with real usage at moderate scaleIn between
2: UsersEveryone in productionGeneral availabilityMost stable; the exposed feature set is smaller

The third slide ("exposed feature set + rings") makes one more point: from early adopters to production users, volatility falls and stability rises, and the set of features switched on shrinks. Feature flags are the mechanism: inner rings have more flags on, and some users get custom exposure.

"Canary" comes from the canary in a coal mine: a small early warning before the danger reaches everyone.

Blast radius

Blast radius is the extent of the damage if a change goes wrong: how many users, services or machines are affected. Much of DevOps practice is a way of shrinking it.

PracticeHow it limits blast radius
Deployment rings / canary releaseOnly a small group sees the change first
Feature flagsOne feature can be turned off without touching the rest
Small, frequent changes (CI)Less can break per change, and the cause is easy to find
Microservices / separate hostsA failure is contained in one service (though dependencies can spread it, as Lamport's quote warns)
Least privilegeA leaked token or compromised host can reach less. WS6: port 3306 open to VM1 only, GRANT SELECT only
Staging / bakingThe first place a bad build explodes is not production

Shift left and shift right

Shift left

Move testing and quality checks earlier, toward plan, design and dev, where defects are cheap to fix.

  • Static analysis and linting at diff time
  • Unit tests on every commit (CI)
  • Pre-commit hooks, pre-build checks
  • Code review before merge
  • Security review early ("Invite Privacy and Security In")

Shift right

Extend testing later, into deploy, operate and measure, because some problems only show with real users, real data and real load.

  • Canary releases and deployment rings
  • A/B tests and feature-flag experiments
  • Monitoring, telemetry, alerting
  • Post-deploy testing in production
  • Chaos engineering (Chaos Monkey)
Exam angleThe two are complements, not rivals. Shift left prevents defects cheaply; shift right detects what could not be predicted and limits its blast radius. Your WS6 benchmark was a shift-right style activity: measuring the deployed system.

Load balancing

  • A load balancer distributes incoming requests across multiple instances of a service.
  • It is the "networking layer" that Lecture 5 says canary and blue-green releases are implemented in.
  • Rollback option 1 from lecture is a load-balancer action: shift traffic away from the canary.
  • WS4 mentioned that nginx in front of Node.js is useful for static caching and load balancing. (The term "reverse proxy" is excluded from the midterm.)

Definitions from this deck

Deployment ringsslide wordingrollout rings
Groups that receive a change in sequence: canaries, early adopters, users.
Canaries
The innermost ring: the first small group exposed to a change.
Early adopters
The middle ring: users who get changes before everyone else.
Blast radius
The scope of impact if a change is bad. It widens as the change is promoted to outer rings.
Approval
A gate between rings in the CD part of the pipeline.
Exposed feature set
The features switched on for a given ring. Larger and more volatile for early adopters; smaller and more stable for production users.

Shift-right
Moving testing later, into deployment and operation (testing in production).

Check yourself

Self-checkWhy does the pipeline on slide 5 trigger automatically into the first ring but require approval for the others?
The first ring has the smallest blast radius, so automatic deployment is low risk. Each later ring exposes more users, so a person (or an automated gate) confirms the change looked healthy before widening.
Self-checkHow do feature flags relate to the "exposed feature set" slide?
Flags are the ON/OFF switches in the picture. They let early-adopter rings see more features than production users and let specific user sets have custom exposure.

Practice

The exam has three question types: true / false with corrections, matching concepts, and naming the tool from a code snippet. "Self-check" and "Read the code" items are for understanding only. On true / false, underline the wrong word and write the fix; a plain "not" earns nothing.
True / FalseIn a ring-based rollout, a change is deployed to all users first and then to canaries.
False. Reverse the order: canaries first, then early adopters, then all users.
True / FalseThe blast radius of a change shrinks as it is promoted to outer deployment rings.
False. Change shrinks to grows. More users are exposed with each ring.
True / FalseShift-left testing means moving testing later in the lifecycle, into production.
False. Change Shift-left to Shift-right (or: shift-left moves testing earlier, toward design and development).
True / FalseCanary releases and monitoring in production are examples of shift-right testing.
True. They test with real users and real traffic after deployment.
True / FalseA load balancer can be used to roll back a canary release by shifting traffic away from it.
True. Rollback option 1 from the lecture.
True / FalseProduction users see a larger exposed feature set than canary users.
False. Change larger to smaller. Inner rings have more new features switched on; production is the most stable.
Self-checkExplain blast radius and name two practices that reduce it.
Blast radius is how much is affected when a change fails: users, services, machines. Deployment rings / canary releases expose few users first; feature flags let one feature be switched off; small frequent changes, least privilege and staging also limit it.
