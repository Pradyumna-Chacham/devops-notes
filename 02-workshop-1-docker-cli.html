Image vs container: the one distinction everything hangs on

A Dockerfile is a text recipe. docker build turns it into an image, a read-only, layered snapshot of a filesystem (a "binary artifact"). docker run starts a container, a running instance of that image with its own thin writable layer on top. One image can start any number of containers, and none of them change the image.

Exam angleExpect a T/F that swaps image and container, for example "docker build creates a container". It creates an image; docker run creates the container.

Reading a Dockerfile

Exact docker syntax is not tested and you will not write code. What the review deck does promise is a "distinguishing code kinds" question: you are shown a snippet and name the tool. So know what a Dockerfile looks like, what each line does, and when it happens (build time or run time).

Exam angleHow to recognise a Dockerfile: every line starts with an instruction in CAPITALS followed by a space, with no colon: FROM, RUN, COPY, WORKDIR, ENV, USER, CMD, ENTRYPOINT. No indentation structure. The first real line is almost always FROM. Do not confuse RUN apk add … (Dockerfile) with - run: … (GitHub Actions) or with a bare docker run … typed in a terminal (a Bash shell command).

Exam angleRUN vs CMD is the classic confusion. RUN happens once while the image is being built. CMD does nothing at build time; it names what runs every time a container starts.

The commands you ran

docker build . -t workshop-1                 # read ./Dockerfile, produce image tagged workshop-1
docker run -it workshop-1                    # new container; -i interactive, -t terminal
docker run -v $(pwd)/scratch:/scratch -it workshop-1    # same, plus a bind mount
exit                                         # leave the shell; the container stops

-it gives you an interactive terminal. Leave it off when the container should just run its program and finish (Workshop 2 does this). . is the build context, the folder that holds the Dockerfile. The "Cannot connect to the Docker daemon" error means the background Docker service is not running.

Why hi.txt disappeared

You ran echo 'hello there!' > hi.txt inside a container, exited, and ls on your laptop showed nothing. Two reasons, and the exam can ask for either:

  1. Isolation. The container has its own filesystem. A file created inside it was never on the host.
  2. Containers are ephemeral. The next docker run starts a brand-new container from the unchanged image, so even inside the container the file is gone.
Same story for software: apk add cloc inside a running container works until that container is gone. To make it permanent, put it in the Dockerfile with RUN and rebuild.

The bind mount: -v host_path:container_path

The study guide names this one explicitly. -v creates a temporary connection between a folder on your machine and a folder inside the container. Both names point at the same files, so a write on either side is immediately visible on the other, and the data outlives the container because it lives on the host.

docker run -v $(pwd)/scratch:/scratch -it workshop-1
#             host folder      path inside the container
# $(pwd) is command substitution: the shell replaces it with the current directory
# Windows PowerShell spelling: ${PWD}/scratch:/scratch
Where you wroteVisible on host?Survives the container?
/hi.txt (no mount)NoNo
/scratch/hi.txt (mounted)Yes, as ./scratch/hi.txtYes, it is a host file
Exam angleThe bind mount comes back in Workshop 4: the Ansible container mounts your workshop folder (so it can read the playbook) and ~/.ssh as /root/.ssh (so it can use your SSH keys without copying keys into the image). If asked "how does a container use a file on the host without baking it into the image?", the answer is a bind mount.

Installing software: running container vs image

apk is the Alpine Package Keeper, a package manager: it knows which pre-built packages exist on internet servers and installs them. apk update refreshes the package list; apk add cloc git installs.

ApproachHowLastsReproducible?
Install by handapk add cloc at the / # promptUntil that container is goneNo. It lives in one person's memory
Bake into imageRUN apk add cloc in the Dockerfile, rebuildEvery container from the imageYes. The recipe is in version control

git clone --depth=1 <url> downloads only the latest snapshot instead of the full history. cloc git then counts lines of code by language; the git project alone has 20+ file types, which is the workshop's point that real projects mix many languages and toolchains.

Getting the repo: ZIP vs git clone

"Download ZIP" gives you the files only. git clone also sets up the connection between your local copy and the git server (history, remotes, the ability to pull and push), and over SSH it needs git installed and SSH keys configured. Know that these are different.

Shell cheat sheet

Exam angleHow to recognise Bash shell commands: one command per line, a program name followed by flags and arguments (ls -l, docker run -it …, ssh user@host, curl -H …, apk add git). Look for pipes |, redirects > and >>, variables with a single dollar sign ($HOME, $(pwd)), export, sudo, cd, echo. No key: value structure and no capitalised instructions. ansible-playbook -i hosts.yaml site.yaml and docker build . -t ws4 are shell commands, even though they run other tools.

A shell (sh, bash, PowerShell) is a program that reads commands and runs them. Lecture gave two reasons to prefer the command line: flexibility / remote access (cloud machines and devices have no screen) and understanding the computational context (you see the variables, files and processes a program really runs in).

Definitions from this deck

Command line / shell
A text interface where a program reads and runs your commands. Preferred for flexibility, remote access, and seeing the computational context.
Docker client
The docker command you type. It sends requests to the daemon.
Docker daemon / host
The background service that builds images and runs containers.
Image
Read-only template built from a Dockerfile.
Container
A running instance of an image.
Registry
Server that stores and serves images.
Dockerfile instructions
FROM base image, ENV variable, RUN build-time command, COPY file into image, USER user, ENTRYPOINT / CMD what runs when the container starts.
Fork
Your own copy of someone else's repository on GitHub, from which you send pull requests back.
Upstream
The original repository your copy tracks.

Practice

The exam has three question types: true / false with corrections, matching concepts, and naming the tool from a code snippet. "Self-check" and "Read the code" items are for understanding only. On true / false, underline the wrong word and write the fix; a plain "not" earns nothing.
True / FalseThe command docker build creates a container from a Dockerfile.
False. Change container to image. docker run is what creates a container.
True / FalseA file created inside a running container is automatically saved back into the image.
False. Change automatically saved back into the image to lost when the container is removed (unless it was written to a bind-mounted folder).
True / FalseIn -v $(pwd)/scratch:/scratch, the path on the left of the colon is the path inside the container.
False. Change inside the container to on the host. Host is left, container is right.
True / FalseIn a Dockerfile, the RUN instruction specifies the program that starts when the container launches.
False. Change RUN to CMD. RUN executes at build time and creates a layer.
True / FalseDownloading a repo as a ZIP sets up the same connection to the git server as git clone.
False. A ZIP is only a copy of the files. git clone creates the link to the remote plus the history.
Self-checkYou ran apk add cloc in a container yesterday. Today cloc is "not found". Why, and what is the lasting fix?
Today's docker run started a new container from the unchanged image; yesterday's install lived only in yesterday's container. Fix: add RUN apk add cloc to the Dockerfile and rebuild, so the software is part of the image.
Self-checkGive two reasons a team would run a build tool inside a container instead of directly on each developer's laptop.
Reproducibility (everyone gets the same OS, tools and versions, which fights bit rot and "works on my machine") and isolation / disposability (nothing is installed on the host; throw the container away and start clean). Lightweight compared with a VM.
Read the codedocker run -v ~/.ssh:/root/.ssh -v $(pwd):/ws4 -it ws4 What do the two -v flags achieve, and why not COPY the keys in the Dockerfile?
They bind-mount the host's SSH key folder at /root/.ssh and the current project folder at /ws4, so the container can use the keys and playbooks while they stay on the host. Copying keys into the image would bake a secret into a shareable artifact; anyone with the image could extract it.
