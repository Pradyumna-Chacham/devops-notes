Configuration management

Slide definition: "A process in which an inventory of software and production assets is provisioned and controlled through package managers and tools such as Ansible." In practice: you describe in files what every machine should look like (packages, services, files, users, firewall rules) and a tool makes the machines match.

The matching adage is "Configuration is Code". Configuration lives in version control, is reviewed in pull requests, and is run by automation, exactly like source code. This is the direct cure for bit rot and for "snowflake" servers that someone configured by hand and nobody can rebuild.

Exam angleThe three properties the lecture objectives listed, word for word: Ansible is agentless, Ansible is declarative, Ansible is idempotent. Any T/F that flips one of these is false. The slides' own sample: "Ansible is mostly an imperative language" → declarative.

Architecture: control node, managed nodes, no agents

Term (and synonyms)Meaning
Control node
a.k.a. controller, Ansible workstation		"Any machine with Ansible installed." You run ansible or ansible-playbook from it. Any computer with Python can be one: laptop, shared desktop, server
Managed nodes
a.k.a. hosts, inventory		"The network devices (and/or servers) you manage with Ansible… Ansible is not installed on managed nodes."
AgentA software program that would have to be installed and kept running on every managed machine. Ansible has none: it is agentless
InventoryThe file listing managed nodes and groups (hosts.yaml)
PlaybookYAML file of plays and tasks describing the desired state
ModuleA unit of work a task calls: apt, service, copy, template, shell, uri…

Why agentless matters: nothing to install, upgrade or secure on every server; a brand-new machine can be managed the moment it accepts SSH; fewer moving parts. The cost is that the control node must be able to reach every host over SSH. Ansible was created by Michael DeHaan (NC State, 2001).

The role of SSH

SSH (secure shell) is Ansible's transport. Because there is no agent, SSH is how the control node gets an encrypted channel to each managed node and runs commands there. Ansible is non-interactive, so nobody is there to type a password: you must set up key-based, password-less login first.

The short way
ssh-keygen                       # make the key pair
ssh-copy-id -i ~/.ssh/id_rsa.pub user@IP
ssh user@IP                      # no password now
The long way (what ssh-copy-id does)
scp ~/.ssh/id_rsa.pub user@IP:   # trailing ":" = home dir
ssh user@IP
mkdir ~/.ssh
cat id_rsa.pub >> ~/.ssh/authorized_keys   # >> appends
rm id_rsa.pub ; exit
  • The first connection asks you to confirm the host's fingerprint ("authenticity of host can't be established"); answer yes once.
  • scp is "secure copy": a file copy that rides on SSH.
  • Never commit SSH keys or tokens. The rubric penalty was −2.

Inventory: the hosts file

Workshop 4 hosts.yaml (INI style)
[myserver]
<VM-IP-ADDRESS> ansible_user=<unityid> ansible_python_interpreter=/usr/bin/python3
Slide example with groups
host1.domain.com
192.168.1.193

[routers]
router1.domain.com
CSR-1 ansible_host=192.168.1.199

[webservers]
www1.domain.com
www2.domain.com
  • [name] defines a group. A play's hosts: line names a group (or all), which is how one playbook can target one machine or a thousand.
  • ansible_user tells Ansible which username to use when it builds its internal ssh command. ansible_host gives an address for an alias.
  • Vocabulary trap: inventory, hosts and managed nodes all mean the same machines.

Playbook anatomy

Exam angleHow to recognise an Ansible file: YAML that starts with a list item - hosts: or - name:, then tasks:; often become:; each task is a name: plus a module such as apt:, yum:, service:, copy:, template:, shell:, uri:; desired-state words like state: present, state: started; variables in plain double braces {{ item }} with no dollar sign; with_items:, notify:, handlers:, register:, when:. An inventory file with [group] headings and host names is also an Ansible file. The review deck's own example began - hosts: all, vars:, tasks:, apt: name={{item}} state=present, with_items: packages.
---                                  # YAML document start
- name: Demo playbook                # a PLAY: maps a group of hosts to tasks
  hosts: myserver                    # which inventory group
  become: yes                        # escalate privileges…
  become_method: sudo                # …using sudo (needed to install packages)
  tasks:                             # ordered list
    - name: Install nginx            # a TASK: human-readable name + one module
      apt:                           # module: Ubuntu's package manager
        name: nginx
        state: latest                # desired state, not a command
    - name: Start nginx service
      service:
        name: nginx
        enabled: true                # start at boot
        state: started               # ensure it is running
    - name: Create a custom index.html file
      copy:
        dest: /var/www/html/index.html
        content: |
          <h1>Hello CSC-519 World!</h1>
    - name: Expose port 80 with iptables
      shell: "sudo iptables -I INPUT -p tcp -m tcp --dport 80 -j ACCEPT"
PieceRead it as
hosts:"Apply this play to these inventory machines"
become: yes"Do this as root via sudo"
state: present"Make sure it is installed" (any version)
state: latest"Make sure it is installed and at the newest available version"
state: started / enabled: true"Make sure the service is running" / "…and starts on boot"
copy with content:"Make sure this file exists with exactly this content"
shell:"Run this command." The imperative escape hatch

Two judgment calls the README raises

  • Latest vs pinned version. latest gets you the newest (as packaged by apt) but a future version may break you. A pinned version is known and repeatable but ages. "There is no perfect answer here, only tradeoffs."
  • Don't inline one language inside another. Embedding HTML in the playbook was "for demonstration purposes only". Normally copy or clone the file from its own source.

Declarative vs imperative

Imperative: HOW (shell script)
# step-by-step control flow, you track state
apt-get update
if ! dpkg -s nginx >/dev/null 2>&1; then
  apt-get install -y nginx
fi
if ! systemctl is-active nginx; then
  systemctl start nginx
fi
systemctl enable nginx
Declarative: WHAT (Ansible)
# describe the end state; the module
# works out whether anything must change
- apt:
    name: nginx
    state: present
- service:
    name: nginx
    state: started
    enabled: true
ParadigmImperativeDeclarative
OperationDefines HOW tasks should be accomplishedDefines WHAT tasks should be accomplished
ComputationDefines the control flow and state changesDefines only the logic
Mutating variablesVery usualUnusual and not recommended
AdvantagesEasy-to-learn notation; machine-architecture compliantEasy-to-optimize code; high abstraction level
DisadvantagesHard debugging; vulnerable to data racesUnfamiliar notation; less customizable code
Derived paradigmsProcedural, object-orientedFunctional, logic

The slide says Ansible is "mostly" declarative for a reason: tasks still run top to bottom, and the shell and command modules are plain imperative commands. Those are where idempotence breaks.

Idempotence

Idempotent: performing the operation again gives the same result. Run a playbook once or ten times and the machine ends in the same state. The slide's picture: looking at a cake is idempotent, eating a slice is not.

HTTP methods (from the slide)

MethodIdempotentSafe
GET, HEADYesYes
PUT, DELETEYesNo
POST, PATCHNoNo

Why it matters

  • Safe to re-run after a failure half-way through
  • Safe to run on a schedule to correct drift
  • The same playbook works on a fresh machine and on a configured one
  • The "changed" count becomes a signal: zero means the machine already matched

Making a shell task idempotent

- name: Initialize the database
  shell: sqlite3 /opt/myapp/data.db < /opt/myapp/init.sql
  args:
    creates: /opt/myapp/data.db     # skip the task if this file already exists

Other guards you used in later workshops: when: (run only if a registered check says so), changed_when: (tell Ansible whether the command really changed anything), SQL IF NOT EXISTS, and "check then insert" (iptables -C … || iptables -I …).

Exam angleIdempotent does not mean "runs only once" or "nothing happens". It means repeated runs converge on the same end state. A first run that changes five things and a second run that changes zero is idempotence working.

Running it from the container

docker build . --tag ws4
docker run -it -v $(pwd):/ws4 -v ~/.ssh:/root/.ssh ws4     # two bind mounts (WS1 idea)
ansible-playbook -i hosts.yaml deploy-webserver.yaml          # inside the container

The README printed a command that was "intentionally wrong in 3 ways": ansible-runplaybook -i ./hosts deploy-webserver.yml. The fixes:

WrongRightWhy
ansible-runplaybookansible-playbookThat is the real command name
-i ./hosts-i hosts.yaml-i points at the inventory file you actually created
deploy-webserver.ymldeploy-webserver.yamlThe file was saved with the .yaml suffix

The picture to hold: the control node is inside a container on your laptop; the container borrows your project folder and SSH keys through bind mounts; the managed node is the remote Ubuntu VM. Visiting http://IP afterwards shows "Hello CSC-519 World!".

Reading the output: each task prints ok (already in desired state), changed (Ansible modified something), or failed, and the play recap totals them per host.

The Node.js playbook (your deploy-node.yaml)

Requirements: install nginx and nodejs, deploy an app you wrote, install npm packages, serve "Hello CSC-519 World!" on port 80, create a SQL database the app reads, and have Ansible itself test that the server is up.

- name: Deploy Node.js app
  hosts: myserver
  become: yes
  tasks:
    - name: Install Node.js and npm
      apt: { name: [nodejs, npm], state: present, update_cache: yes }
    - name: Copy app files to remote
      copy: { src: app/, dest: /opt/myapp/ }          # control node → managed node
    - name: Install npm dependencies
      npm: { path: /opt/myapp }
    - name: Initialize the database
      shell: sqlite3 /opt/myapp/data.db < /opt/myapp/init.sql
      args: { creates: /opt/myapp/data.db }           # idempotence guard
    - name: Install systemd service for the app
      template: { src: templates/myapp.service.j2, dest: /etc/systemd/system/myapp.service }
    - name: Reload systemd and start app
      systemd: { name: myapp, state: restarted, enabled: yes, daemon_reload: yes }
    - name: Wait for app to come up
      uri: { url: "http://localhost:80", status_code: 200 }
      register: result                                # save the module's output
      until: result.status == 200                     # retry loop
      retries: 5
      delay: 2
  • Don't get stuck. shell: node server.js would never return, and the playbook would hang. Running the app as a systemd service starts it in the background, restarts it on failure, and survives reboots.
  • The uri task is a test in the pipeline. The playbook fails loudly if the app does not answer 200, instead of reporting success for a broken deployment.
  • template vs copy: a .j2 template can contain {{ variables }} that Ansible fills in; copy transfers a file as is.

Practice

The exam has three question types: true / false with corrections, matching concepts, and naming the tool from a code snippet. "Self-check" and "Read the code" items are for understanding only. On true / false, underline the wrong word and write the fix; a plain "not" earns nothing.
True / FalseAnsible is mostly an imperative language.
False. Change imperative to declarative. (Sample question from the slides.)
True / FalseAnsible requires an agent program to be installed on every managed node.
False. Change requires an agent program to requires no agent: it is agentless and connects over SSH.
True / FalseThe control node is the remote server that Ansible configures.
False. Change control node to managed node (host). The control node is where Ansible is installed and run.
True / FalseAn idempotent playbook produces a different end state each time it is run.
False. Change a different to the same.
True / FalseAnsible uses HTTP to connect from the control node to managed nodes.
False. Change HTTP to SSH.
True / FalseIn Ansible, "inventory", "hosts" and "managed nodes" refer to the same thing.
True. The machines Ansible manages, listed in the hosts file.
True / FalseA declarative program defines HOW tasks should be accomplished.
False. Change HOW to WHAT (or change declarative to imperative).
True / FalseThe shell module is guaranteed to be idempotent.
False. It runs an arbitrary command every time. You must add a guard such as creates: or when:.
True / FalseTo let Ansible log in without a password, you copy your private key to the managed node.
False. Change private to public. The public key goes into ~/.ssh/authorized_keys; the private key never leaves the control node.
True / FalseOf the HTTP methods, POST is idempotent and GET is not.
False. Swap them: GET is idempotent (and safe); POST is not.
Read the codeA playbook has apt: name=nginx state=latest. Give one advantage and one risk compared with pinning a version.
Advantage: you always get the newest packaged version, including fixes, without editing the playbook. Risk: a future version may introduce breaking changes, and two runs on different days can produce different machines. Pinning is repeatable but the pinned version grows old.
Read the codeOn the second run of your playbook, "Install nginx" reports ok but "Expose port 80 with iptables" reports changed. Explain.
apt is a module that checks state and found nginx already installed, so it did nothing. shell simply ran the iptables -I command again, inserting a duplicate rule. The shell task is not idempotent.
Self-checkWhy does Ansible need password-less SSH, and what would happen without it?
Ansible connects to each managed node over SSH automatically, with no human present. Without key-based login it would stop at a password prompt (or fail), so automation across many hosts would be impossible.
Self-checkGive two benefits of an agentless design.
Nothing to install, update or secure on each managed machine; a newly provisioned server is manageable immediately with only SSH and Python; fewer running components and a smaller attack surface.
Self-checkDefine configuration management in one sentence and name the adage that goes with it.
A process in which an inventory of software and production assets is provisioned and controlled through package managers and tools such as Ansible. Adage: "Configuration is Code".
MatchingWhich column does each belong in (Actions only / both / playbooks only)? (a) tied to Git events (b) YAML (c) executed from a control node (d) runs on a runner.
(a) Actions only. (b) Both. (c) Playbooks only. (d) Actions only.
