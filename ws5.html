What Workshop 5 builds

Playbook 0: security updates

- name: Apply system security updates
  hosts: all                         # every machine in the inventory, whatever its group
  become: true
  tasks:
    - name: Refresh the package index
      apt: { update_cache: true, cache_valid_time: 3600 }
    - name: Upgrade all packages to latest security patches
      apt: { upgrade: dist }
    - name: Remove packages no longer required
      apt: { autoremove: true }
    - name: Check whether a reboot is required
      stat: { path: /var/run/reboot-required }
      register: reboot_required        # save the result in a variable
    - name: Reboot host if required by updates
      reboot: { reboot_timeout: 300 }
      when: reboot_required.stat.exists   # conditional task
  • Patching as code. The same file patches one VM or the whole fleet, can run on a schedule, and its history is in git. This is "Configuration is Code" applied to security, and it speaks to the adage "Invite Privacy and Security In".
  • Idempotent by nature. A patched host reports nothing to change.
  • register + when is the standard "look, then decide" pair: gather a fact, then run a task only if needed.

Playbook 1: environment, datastore, app

- name: Configure VM1 with Node.js app and MySQL datastore
  hosts: myserver
  become: true
  vars_prompt:                          # ask at run time; the password is never in the repo
    - { name: db_password, prompt: "Enter password for the MySQL application user", private: true }
  vars:
    db_name: pointsdb
    db_user: appuser
    app_dir: /opt/nearest-app
  tasks:
    - name: Install Node.js, npm, and MySQL server
      apt: { name: [nodejs, npm, mysql-server], state: present }
    - name: Ensure MySQL service is started and enabled
      service: { name: mysql, state: started, enabled: true }
    - name: Create application database
      command: mysql -u root -e "CREATE DATABASE IF NOT EXISTS {{ db_name }};"
      changed_when: false
    - name: Check whether points table already has data
      command: mysql -u root {{ db_name }} -N -B -e "SELECT COUNT(*) FROM points;"
      register: points_count
      changed_when: false
    - name: Import CSV data into points table
      command: mysql -u root {{ db_name }} -e "LOAD DATA INFILE … INTO TABLE points …"
      when: points_count.stdout | int == 0      # import only into an empty table
    - name: Deploy application server.js
      copy: { src: app/server.js, dest: "{{ app_dir }}/server.js" }
      notify: restart nearest-app             # queue the handler if this task changed
    - name: Deploy systemd unit for the application
      template: { src: app/nearest-app.service.j2, dest: /etc/systemd/system/nearest-app.service }
      no_log: true                            # the rendered file contains the password
      notify: restart nearest-app
    - name: Apply pending restarts before verifying the app
      meta: flush_handlers
    - name: Verify the app responds on port 80
      uri: { url: "http://127.0.0.1/", return_content: true }
      register: app_response
      until: app_response.status == 200
      retries: 10
      delay: 3
  handlers:
    - name: restart nearest-app
      systemd: { name: nearest-app, state: restarted, daemon_reload: true }

Ansible keywords you should be able to read

KeywordWhat it does
vars: / {{ name }}Define variables; substitute them with Jinja2 double braces
vars_prompt: + private: trueAsk the operator for a value at run time without echoing it. Keeps secrets out of the repo
register: xStore a task's result (stdout, return code, status…) in variable x
when:Run the task only if the condition is true
changed_when: / failed_when:Override Ansible's idea of whether a command changed something or failed
notify: / handlers:Run a handler (usually a restart) once, later, only if the notifying task changed
meta: flush_handlersRun queued handlers now instead of at the end of the play
until: / retries: / delay:Retry a task until a condition holds
no_log: trueHide this task's inputs and outputs from logs (secrets)
template:Render a .j2 file with variables, then copy it to the host
wait_for: / uri:Wait for a port to open / make an HTTP request and check the status
hosts: allTarget every host in the inventory

Exam angleThe second row is a configuration-management idea worth a short answer: a playbook is only proven if it works on a fresh machine. A VM you have poked by hand has hidden state, so "it works on my VM" proves nothing. Reproducibility is the point.

Idempotence patterns in a real playbook

PatternWhere you used itEffect on a second run
Declarative moduleapt: state=present, service: state=started, file: state=directoryReports ok, does nothing
Idempotent commandCREATE DATABASE IF NOT EXISTS, CREATE TABLE IF NOT EXISTSThe SQL itself is a no-op
Check, then actSELECT COUNT(*) → register → import when count is 0Import is skipped; no duplicate 10,000 rows
Guard filestat node_modules → npm install only when missing or package.json changedSkipped
Honest reportingchanged_when: false on read-only commands"changed" count stays meaningful
HandlersRestart only on notifyNo needless restart, no downtime

Without the count check, every run would load the CSV again and the "nearest point" query would return duplicates from a table of 20,000, then 30,000 rows. That is the concrete cost of a non-idempotent task.

The app: let the database do the work

The app answers GET / by generating a random point in (0,0)–(100,100) and finding its nearest neighbour among 10,000 stored points. The README forbade loading the dataset into Node's memory, so the distance is computed in SQL and only the winning row comes back:

SELECT x, y, SQRT(POW(x - ?, 2) + POW(y - ?, 2)) AS distance    -- Cartesian distance
FROM points
ORDER BY distance ASC
LIMIT 1;
systemd unit template (.j2)
[Service]
ExecStart=/usr/bin/node {{ app_dir }}/server.js
Restart=always
Environment=PORT=80
Environment=DB_HOST=127.0.0.1
Environment=DB_USER={{ db_user }}
Environment=DB_PASSWORD={{ db_password }}
server.js reads them
const PORT = Number(process.env.PORT) || 80;
const pool = mysql.createPool({
  host: process.env.DB_HOST || "127.0.0.1",
  user: process.env.DB_USER || "appuser",
  password: process.env.DB_PASSWORD || "",
  database: process.env.DB_NAME || "pointsdb",
});
Exam angleThis is the environment-variable idea from Workshop 2 again. The code contains no host name or password; configuration is injected by the environment, so the same server.js runs unchanged in Workshop 6 when only DB_HOST changes to point at another machine.

Continuous deployment and Glossary 1

The lecture's source is "The Top 10 Adages in Continuous Deployment" (IEEE Software, 2017; authors from Microsoft, SAS, Red Hat, Mozilla, Cisco, IBM, Oracle, LexisNexis and NC State). Learn these five definitions close to verbatim.

TermDefinition (Glossary #1)
Continuous DeploymentA process in which incremental software changes are automatically tested, vetted, and deployed to production environments
Feature FlagsA mechanism for dynamically enabling features during production, often controlled by a global in-memory store and cached locally in service instances
Dark LaunchingA practice in which code is incrementally deployed into production but remains invisible to users
Deflighting or RollbackA method for rolling back or decommissioning a defective change and removing it from the deployment pipeline
"Staging" or "Baking"A stage in the deployment pipeline in which developers test a new software version in a production-like environment. Some companies bake a new version for eight hours before deployment

Deploying is not releasing

  • Deploy: the new code is installed and running in production.
  • Release: users can see and use the feature.

Feature flags

Also called toggles, release toggles or feature flippers. They are "how deployed features become released features".

What it looks like in code (pseudocode)
if (flags.isEnabled("new-checkout", user)) {     // looked up at RUN TIME, no redeploy needed
    renderOneClickCheckout();                     // deployed, shown only when the flag says so
} else {
    renderOldCheckout();
}

What flags buy you

  • Deploy without releasing (dark launch)
  • Easy, fine-grained rollback: switch one feature off
  • Target by rule or group: VIPs, beta testers, a percentage, IP allowlist
  • Run experiments (A/B tests)

What they cost

  • Stale flags are technical debt. Slides: "sub-optimal flag management that makes information on staleness of flag ambiguous" and "lack of developer incentives to clean up source code related to stale flags"
  • Possible bad user experience: features appear and vanish; users see different things
  • More code paths to test

Dark launching

"Deployed but not released." Enabled by feature flags. Uses listed in lecture:

  1. Release an experimental one-click checkout to see if it increases sales
  2. Test new application infrastructure without switching all traffic
  3. Roll out to VIP users first
  4. Release a feature for beta testing in the real environment

Martin Fowler's variant: run a re-implemented feature in parallel. Old and new code are both called and their results compared, "but only one answer returned to the interface". Users notice nothing while you learn whether the new algorithm agrees.

Experiments and rollout methods

Adage 1: "Every Feature is an Experiment." In continuous deployment a feature has to demonstrate that it is useful: ROI, customer retention, engagement, conversion rate.

Feature flagsCanary release
PlacementApplicationInfrastructure / networking layer
Orchestrated byDevelopers, product managers, QADevOps, SREs
Percentage of traffic / usersYesYes
Whitelisting IP addressesYesYes
Rule-based (app rules, e.g. number of songs in a playlist)YesNo
Group-based (domain, tier…)YesNo
RollbackGranular: one specific featureThe entire deployment
Exam angleKeep the three apart. A/B testing answers "which variant is better?" (an experiment with a metric). Canary answers "is the new version safe?" (risk reduction with a small share of real users). Dark launch has code in production that users cannot see at all.

De-flighting, rollback and load balancing

Two options from the slide, and one rule:

  1. Use the load balancer to shift traffic away from the canary release(s). Infrastructure level; removes the whole new version from service.
  2. Disable the feature flag. Application level; "send a signal to the application to disable the feature". Needs a push update or equivalent.

"In any case, have a rollback plan."

A load balancer sits in front of several instances and decides which one each request goes to. That routing decision is what makes canary (10% to v2), blue-green (flip 100%), rollback (send 0% to the bad version) and scaling possible. See Workshop 6 for the picture.

"The cost of change is dead" (with an asterisk)

Error found duringCost ratio
Requirements1
Design3–6
Coding / implementation10
Development testing (unit)15–40
Acceptance testing30–70
Operation (field)40–100

Adage 2 says this curve is "dead" in continuously deployed systems: when a fix can reach production in minutes and a flag can switch a feature off, a production bug is no longer 100 times dearer. The asterisk: the old curve "still applies to many real-world systems: airplanes, power plants, aircraft carriers".

Practice

Answer in your head first, then open each one. On the real T/F questions you underline the wrong word and write the fix. A plain "not" earns nothing.
True / FalseDark launching is a practice in which code is deployed into production and is immediately visible to all users.
False. Change is immediately visible to all users to remains invisible to users.
True / FalseFeature flags allow a feature to be released without being deployed.
False. Swap the words: flags allow a feature to be deployed without being released.
True / FalseWith feature flags, rollback applies to the entire deployment, while a canary release can roll back one specific feature.
False. Swap them: flag rollback is granular (a specific feature); canary rollback is the entire deployment.
True / FalseCanary releases are usually implemented in the application code by developers and product managers.
False. Canary lives at the infrastructure / networking layer and is orchestrated by DevOps / SREs. Feature flags are the application-level tool.
True / False"Baking" is a stage in which a new software version is tested in a production-like environment.
True. Also called staging. Some companies bake for eight hours.
True / FalseAccording to "The cost of change is dead", fixing an error in operation is always 40 to 100 times more expensive than in requirements.
False. That is Boehm's 1981 finding for plan-driven projects. The adage says it is much less true in continuously deployed systems (though still true for airplanes and power plants).
True / FalseStale feature flags are a form of technical debt.
True. Nobody is rewarded for removing them, and it is unclear which are still needed.
True / FalseIn an Ansible playbook, a handler runs every time the play runs.
False. A handler runs only when a task that notifies it reports changed, and then only once.
True / FalseA/B testing sends about 5% of users to the new version to check that it is safe before widening the rollout.
False. That describes a canary release. A/B testing splits users between variants to compare a metric such as conversion.
Read the codewhen: points_count.stdout | int == 0 sits on the CSV import task. What problem does it prevent?
Importing the 10,000 rows again on every run. The earlier task counted the rows and registered the result; the import runs only when the table is empty, which makes the playbook idempotent.
Read the codeWhy is no_log: true on the task that templates the systemd unit, and why is the password asked with vars_prompt?
The rendered unit contains DB_PASSWORD, so its content must not be printed in Ansible's output or logs. vars_prompt with private: true gets the password from the operator at run time, so it is never written in the playbook or committed to the repo.
Short answerWhat is the difference between deploying and releasing, and which adage does it support?
Deploying puts code into the production environment; releasing makes the feature available to users. Feature flags separate the two. Adage: "Be fast to deploy but slow (or slower) to release."
Short answerGive the two rollback options from lecture and one difference between them.
(1) Use the load balancer to shift traffic away from the canary; (2) disable the feature flag. The load balancer acts at the infrastructure level on the whole version; the flag acts at the application level on one feature and needs a push update or equivalent.
Short answerWhy does the instructor recommend re-provisioning a fresh VM before submitting an Ansible workshop?
A VM that has been modified by many trial runs holds hidden state, so a passing run proves nothing about the playbook alone. Running on a fresh instance shows the playbook reproduces the full configuration from scratch.
MatchingMatch each to an adage: (a) feature flags and canaries (b) A/B testing (c) Ansible playbooks in git (d) Boehm's cost curve.
(a) Be fast to deploy but slow(er) to release. (b) Every feature is an experiment. (c) Configuration is code. (d) The cost of change is dead.
