Deck 0 · Intro and what is DevOps

0_Intro_and_what_is_DevOps.pdf · 29 slides · goes with the WS2 page (Git Flow) and WS3 page (lifecycle)

The first lecture has two real topics after the course logistics: the Git Flow development process, and a first answer to "what is DevOps?". The Git Flow diagram carries a yellow "important slide" star.

SlidesWhat they say and what to know
2–12 · AdminCourse structure. Worth knowing only: exams are on paper, in class, with pen or pencil; the project is a DevOps pipeline built in the second half of the semester.
14 · Software development as a "lifecycle"The classic cycle: planning → analysis → design → implementation → testing and integration → maintenance, and round again. DevOps speeds up and automates the trip around this loop.
15 · Git Flow (important slide)Five lanes: main, hotfix, release, develop, feature. Main carries version tags (v0.1, v0.2, v1.0). Know which lane branches from which and where each merges.
16 · A main branch… with tagsMain alone is a short line of tagged, released versions.
17 · HotfixA hotfix leaves main at v0.1 and returns to main as v0.2: the short path for an urgent production fix.
18 · Main and dev"main stays clean. Don't break the build. Build from main. Use release tags." And: "Quality gates protect main. Dev might at times be broken."
19 · Feature branchesBranch off develop, merge back to develop. Name them unity_id__description. "Don't squash commits (at first)."
20–21 · What is DevOps? It's about perspective"'DevOps' is a set of practices designed to help teams build, test, and release software faster and more reliably." Development on one side, Operations on the other.
22–26 · The infinity loop and tool landscapeSeveral drawings of the same Dev/Ops loop (create, plan, verify, package | release, configure, monitor; or code, build, test | release, deploy, operate, monitor) surrounded by tools: git, Docker, Ansible, Jenkins, Kubernetes, Grafana. Point: DevOps is a crowded set of tools hung on one loop. Slide 26 shows feature branches merging to master and flowing through staging → UAT/QA → prod.
27 · A linear perspectiveDev: plan, develop, build, test. Ops: release, deploy, operate, monitor. Underneath: continuous integration → continuous delivery → continuous deployment → continuous testing → continuous operations.
28 · DevOps is "event-driven"Code commit · pull request to a special branch · automated testing · passing tests might automatically trigger the CI/CD pipeline.

Release and hotfix only. Main must stay clean and buildable because releases are built and tagged from it; features are integrated on develop first.

Code commit; pull request to a special branch; automated testing; passing tests automatically triggering the CI/CD pipeline.

Dev: plan, code (develop), build, test. Ops: release, deploy, operate, monitor.

Deck 1 · Continuous delivery

1_Continuous_delivery.pdf · 48 slides · goes with the WS2 page (diff time, REST) and WS3 page (pipeline, roles)

Objectives on slide 7: roles in DevOps teams, "diff time", a review of REST APIs, CI/CD, and DevOps and CI/CD. This is the densest deck for definitions.

SlidesWhat they say and what to know
8–10 · Git Flow "special moments"Slide 9 highlights the two inbound edges to main: from hotfix and from release. Slide 10 highlights the inbound edges to develop: finished features and fixes merged back.
11 · Continuous Integration"Continuous" is imprecise because code changes happen at discrete moments called diff time. PRs can include one or more commits. Integrating frequently in multi-person teams makes problems easier to identify. Smaller changes → easier debugging. Aim for the "Goldilocks" level of granularity.
12 · An SE event: "diff time"Critical moment in the SE process. This is when code peer review happens (Modern Code Review; Google 2018). Increasingly, this is when static analysis happens (Facebook 2019).
13 · Continuous Deployment"Continuous" is imprecise again: production updates happen at intervals. It is the CD part of CI/CD.
14–16 · DevOps pipelineBuilt up in three steps. C (code) → P (production). Then with TESTING (unit / integration / QA) and STAGING (staging / deployment) between. Then the full example: C → Testing → Build Release → User Acceptance Testing (UAT) → Staged Code "pre-deploy" → P. The stretch up to staged code is labelled "Continuous Delivery".
17 · Events or triggersCode commit; pull request to a special branch; automated testing; passing tests (a "quality gate") can automatically trigger pipeline promotion to the next phase, i.e. "staging".
18 · DevOps environmentsDevelopment (Dev), Testing (Test/QA), Staging (Staging/UAT), Production (Prod). Others: Integration, Disaster Recovery (DR).
19 · ActivityThink-pair-share: "What could go wrong in a DevOps pipeline?" See the model answer below.
20 · Two large pizzas ruleAt Amazon, teams should be no larger than what two pizzas can feed. "This depends on the pizza."
21 · Team rolesService Owner, Gatekeeper, Release Engineer / Coordinator, DevOps Engineer, Reliability Engineer. Learn each one's responsibility.
22–24 · Job postingsNot on the midterm.
25–26 · Services and microservicesA service is exposed over a public, well-defined interface (a set of REST APIs). Each team owns a separate service. Many independent services = a "microservices architecture". Lamport's quote about distributed systems.
27 · TermsProvisioning. Toolchain.
REST review (rest of deck)Roy Fielding's thesis; APIs as "how can my software talk to other software?"; REST consumes and produces JSON over HTTP verbs; the verb table (GET retrieve, DELETE delete, POST create, PUT update); API design principles (Bloch); architectural properties and constraints; nouns as resources (/dogs, /dogs/1234); associations (/owners/5678/dogs); query parameters; error codes 200, 201, 400, 500; versioning, pagination, partial response, authentication; XML vs JSON.

Activity prompt and a model answer

Short answerWhat could go wrong in a DevOps pipeline?
Tests that are missing, weak or flaky let a bad change through, or block good ones. A broken build stops the whole team. Staging differs from production, so something passes there and fails live. Secrets leak into the repo, logs or images. The pipeline is slow, so people bypass it. A bad deploy has no rollback plan. The pipeline's own configuration is wrong. And an automated path to production is itself a target, so its credentials need least privilege.

Check yourself

Short answerWhy does lecture call "continuous" imprecise for both CI and CD?
Code changes arrive at discrete moments (diff time), and updates to production happen at intervals. Neither is literally continuous.
Short answerName the stages of the example pipeline on slide 16 in order.
Code → Testing → Build Release → User Acceptance Testing → Staged code ("pre-deploy") → Production.
Short answerWhich role decides whether to back out a release, and which role watches the system right after deployment?
The Release Engineer / Coordinator makes the back-out decision. The Reliability Engineer is responsible for the period immediately after deployment.

Deck 2 · Computing environments

2_Computing_Environments.pdf · 30 slides, from Dr. Chris Parnin · goes with the WS1 page

Objectives: what is "bit rot"? What is hard about managing computing environments? The different types of environment. A basic intuition for how VMs work.

Slides (in order)What they say and what to know
Does code rot?Two quotes argue that code itself does not wear out (Dijkstra on "software maintenance"; Spolsky: old code "doesn't acquire bugs just by sitting around on your hard drive"). The next slide answers: the world changes around the software. It lives in an ecosystem of dependencies and environments that are not static. Examples shown: Y2K-style date fixes expiring, Facebook's outage, a Roblox outage.
Even simple code snippets can be difficult to run / the default experience is failureA three-line plotting notebook fails with ModuleNotFoundError: No module named 'seaborn'. "It works on my machine."
Managing environments is hardThe tangled Python-install cartoon. "Programmers must be 'end-user' system admins." Many replies say "dependencies". Activity: have you ever had issues with running code?
Your billion dollar idea is worth $0"Software on your machine has no real value." (A recruiter asks for links to projects; the answer is "localhost:3000".)
Where does your code live and run?Consider not only code but its dependencies, environment, software ecosystem, stakeholders and users, and value. Think of building computing environments: configuration + code. "Resilient and scalable software co-exists with infrastructure."
Properties of an ideal environmentReproducible, resilient, secure, scalable, flexibility, maintain quality of service, resource utilization. (Presented as fill-in-the-blank.)
Classic VMs vs headless infrastructureClassic: fully loaded OS, graphical interface, optimized, heavy-weight. Headless (headless VMs, micro VMs, containers): "you can build, use, and throw away".
TermsPopek and Goldberg's VM definition; host/hypervisor; guest; VMM; privileged instructions.
Full emulationThe fetch–decode–switch loop: run the VM as a user application and emulate CPU, memory, disks, network. "Problems?" → it is slow.
OptimizationsTrap-and-emulate: ADD/SUB run directly; a syscall traps to the VMM. Binary translation: the unsafe syscall is rewritten into a safe "virtcall".
Hardware-assisted / paravirtualizationVT-x adds a guest mode and instructions such as VMREAD; the VMM is easier to implement. Paravirtualization patches the guest OS.
Examples and trendsFull emulation: Bochs, PDP-10, video games. Trap-and-emulate: System/370. Binary translation: QEMU, VMware, VirtualBox. Hardware-assisted: KVM, ESXi, Hyper-V. Paravirtualization: Xen, Hyper-V, Hyperkit. AWS moved from Xen to KVM.
OS-level virtualizationThe OS provides mechanisms for virtualizing resources; not full virtualization. The cartoons show the building blocks: chroot (a different root directory) and cgroups (limits on memory and CPU).
VMs vs containers (vs unikernels)VM: app + guest OS/kernel on a hypervisor on hardware. Container: container on a shared OS + kernel on hardware. Unikernels are not on the midterm.
No one best computing environmentBare metal: desktop/mobile/embedded, efficiency, CI harness. Headless virtualization: general-purpose services. OS-level virtualization: self-contained processes. Micro VMs: embedded appliances such as Docker for Mac and WSL. Firecracker is still a foundation of AWS.

Activity prompt and a model answer

Short answerHave you ever had issues with running code? What was the cause?
A typical answer: a project that ran last semester now fails because a library released a breaking version, the interpreter was upgraded, or a package is not installed on this machine. The cause is the environment, not the code. The fix is to write the environment down (Dockerfile, pinned versions, a playbook) so it can be rebuilt.

Check yourself

Short answerIf code does not wear out, why does it "rot"?
Because software depends on an ecosystem (libraries, OS, services, hardware) that keeps changing. The code is the same but its assumptions stop being true.
Short answerWhy is full emulation slow, and what do the optimizations do about it?
Every guest instruction is interpreted in software. Trap-and-emulate and binary translation let safe instructions run directly on the CPU and handle only privileged ones specially; hardware-assisted virtualization moves that support into the CPU.
Short answerGive the use case for bare metal, headless VMs, containers and micro VMs.
Bare metal: desktop, mobile, embedded, efficiency, CI harness. Headless VMs: general-purpose computing services. Containers (OS-level): self-contained processes. Micro VMs: embedded appliances such as Docker for Mac and WSL.

Deck 3 · Configuration management

3_Configuration_Managment.pdf · 30 slides · opening quote "Configuration Is Code" · goes with the WS4 page

Objectives on slide 4, word for word: Ansible is agentless, Ansible is declarative, Ansible is idempotent, and learn about "inventory", also known as hosts, a.k.a. managed nodes.

SlidesWhat they say and what to know
4 · DefinitionConfiguration management: "A process in which an inventory of software and production assets is provisioned and controlled through package managers and tools such as Ansible."
5–8 · Intro to AnsibleCreated by Michael DeHaan (NC State, 2001); acquired by Red Hat in 2015. Wikipedia's description: a suite of tools that enables infrastructure as code: provisioning, configuration management, application deployment. Agentless, relying on temporary remote connections via SSH.
9 · Ansible at a high levelInventory + playbook feed the Ansible workstation (a.k.a. control node), which reaches each server over an SSH connection. "No ansible agents (software program) installed!"
10–11 · ArchitectureUsers write a playbook; Ansible has an inventory, modules, an API and plugins; it acts on hosts and networking in a public or private cloud.
12–13 · Where Ansible fits in the lifecycleIn the plan → code → CI → build → test → deploy → monitoring loop, Ansible covers CI/build, test, and deploy/continuous management. One control node with a host inventory and playbook reaches Dev, QA, UAT and Prod over SSH.
14–15 · EcosystemAnsible integrates with version control, secrets management, infrastructure (AWS, Azure), containers, build and test tools, operating systems. Competitors named: Chef, Puppet, SaltStack, Rudder.
16–17 · Ansible is declarativeThe imperative vs declarative table: HOW vs WHAT; control flow and state changes vs only the logic; mutating variables very usual vs unusual; advantages and disadvantages; derived paradigms.
18–19 · Control nodes and managed nodesControl node: any machine with Ansible installed (needs Python). Managed nodes: the devices or servers you manage, also called hosts; Ansible is not installed on them.
20 · "Inventory" in hosts.yamlUngrouped hosts by name or IP; groups in brackets ([routers], [webservers]); a per-host variable (CSR-1 ansible_host=192.168.1.199).
21 · Playbook example 1install_webserver.yaml: name, hosts: webservers, become: yes, two tasks using ansible.builtin.apt (state: present) and ansible.builtin.service (state: started, enabled: yes).
22 · Idempotence"When performing an operation again gives the same result." Cake: looking is idempotent, eating a slice is not. HTTP table: GET, HEAD, PUT, DELETE idempotent; POST, PATCH not; only GET and HEAD are safe.
23 · Playbook example 2Annotated: (1) name of playbook, (2) host group name, (3) sudo / run-as-different-user setting (become, become_user), (4) tasks. Uses yum for Apache with state: latest, then service with state: started.
24 · GitHub Actions and Ansible playbooksThree columns. Actions only: not always idempotent; automates the repo lifecycle, tied to Git events; runs on a runner, each job in a clean environment; can run playbooks. Both: YAML, declarative syntax, used in CI/CD. Playbooks only: always idempotent; automates configuration management and application deployment; executed from a control node that connects to target nodes; does not trigger GitHub Actions.
25 · What Ansible managesSwitch configuration, automated job execution, database configuration, security and compliance, VM provisioning, application integration and deployment, across network devices, bare metal and virtual, private and public cloud.
26–29 · AI and AnsibleThink-pair-share on prompting; Ansible Lightspeed (Red Hat's AI for Ansible): proprietary, specialist AI, comment-completion workflow. A paper on security smells in Ansible and Chef scripts.
30 · SummaryAnsible is a configuration management tool. Ansible is agentless.

Activity prompt and a model answer

Short answerAI prompts and Ansible: how can I get better results for configuration management tasks?
Give the model the context a human would need: target OS and version, the inventory groups, which packages and versions, and where files should go. Ask for real modules instead of shell, ask for idempotent tasks, and ask it to explain each task. Then verify: run it against a freshly provisioned VM, run it twice and expect zero changes the second time, and never paste secrets into the prompt.

Check yourself

Short answerState the three properties of Ansible from the objectives slide.
Agentless, declarative, idempotent.
Short answerFill in the comparison: Actions only / both / playbooks only for "YAML", "tied to Git events", "always idempotent", "executed from a control node".
YAML: both. Tied to Git events: Actions only. Always idempotent: playbooks only. Executed from a control node: playbooks only.
Short answerWhy is PUT idempotent but POST not?
PUT sets a resource to a given state, so repeating it leaves the same state. POST creates a new resource each time, so repeating it creates duplicates.

Activity prompt and a model answer

Short answerWhat's the difference between deploying and releasing, and what could go wrong from a user's perspective?
Deploying installs the code in production; releasing switches the feature on for users. From the user's side: features appear and disappear without warning; two people see different versions of the same app; a half-finished feature leaks out; support cannot reproduce "my screen looks different"; the user is part of an experiment they did not choose.

Check yourself

Short answerGive two of the four dark-launch use scenarios.
Release an experimental one-click checkout to see if it increases sales; test new application infrastructure without switching all traffic; roll out to VIP users first; release a feature for beta testing.
Short answerIn the feature-flags-vs-canary table, which rows differ?
Placement (application vs infrastructure networking layer), orchestrated by (developers, PMs, QA vs DevOps, SREs), rule-based and group-based targeting (flags yes, canary no), and rollback (specific feature vs entire deployment).
Short answerWhat does the asterisk on "The cost of change is dead*" mean?
It holds in continuously deployed systems. For many real-world systems such as airplanes and power plants, Boehm's rising cost still applies.

Check yourself

Short answerExplain "pipe" and "filter" using a DevOps pipeline.
Each stage (build, test, analysis…) is a filter: it takes the unit of change in, does one job, and passes the result on. The hand-off between stages is the pipe.
Short answerWhat does it mean that "pipelines are just integrative technology"?
The pipeline does not compile, test or analyze anything itself. It connects and sequences other tools (make, maven, npm, linters, test runners) and decides whether the change moves on.

Pain: troubleshooting why a build failed, and long build times. Benefit: catching errors earlier (detecting and fixing defects faster).
