Git Flow, branches and code review

Git
A distributed version control system: it records the history of a project as commits and lets many people work on branches and merge them.
Clone vs download ZIP
git clone copies the repository and sets up the connection to the git server (history, remote, push and pull). A ZIP is only a snapshot of the files with no connection.
Commit
One recorded change to the repository, with a message. Workshop 2 asked for meaningful commit messages.
Branch
A named, movable pointer to a commit (a "ref"). Creating a branch is cheap, which is why work is isolated on branches.
Branch-based development
Nobody commits straight to the shared branch. Work happens on a short-lived branch and enters the shared branch only through a reviewed merge.
Git Flowslide wordinga Git-based development workflow
A branching model with five kinds of branch: main, develop, feature, release and hotfix, and fixed rules for which may merge into which.Marked "important slide" in lecture.
mainslide wording
The clean, always-buildable branch. "main stays clean. Don't break the build. Build from main. Use release tags." Quality gates protect main.Only release and hotfix branches merge into main: its two inbound edges.
developslide wordingdev
The integration branch, branched from main. Finished features merge here. "Dev might at times be broken."Receives features, plus the merge-backs from hotfix and release.
Feature branchslide wording
Branched from develop and merged back into develop. Named unity_id__description. "Don't squash commits (at first)."Sample exam question: "a feature branch is branched from main" is false. Correct word: develop.
Release branch
Branched from develop to stabilise a version. Merges into main (where it gets a tag) and back into develop.
Hotfix
An urgent production fix branched from main. Merges into main and also into develop so the fix is not lost.
Tag / release tag
A fixed label on a commit on main marking a version, such as v0.1, v0.2, v1.0.
Squash
Combining several commits into one before merging. The slides say not to squash at first, so the history of the work stays visible.
Pull request (PR)
A request to merge one branch into another. It holds one or more commits, shows the diff, hosts the review discussion, and is where automated checks report.
Diff timeslide wording
The critical moment in the software engineering process when a code change is proposed. It is when peer code review happens and, increasingly, when static analysis runs.It is a discrete event, which is why "continuous" is called imprecise.
Modern Code Reviewslide wording
Peer review of code changes at diff time, done with tools on the diff instead of in formal inspection meetings. Source: "Modern code review: a case study at Google" (2018).
Static analysis
Automated checking of code without running it (linters, bug finders). Increasingly run at diff time. Source: "Scaling static analyses at Facebook" (2019).
Quality gate
A check a change must pass before it is promoted to the next stage or branch, for example "all tests pass". Gates may be automated.
.gitignore
A file listing paths git must not track. Used to keep mytoken.txt, keys and inventory files out of the repository.

DevOps, lifecycle and pipelines

DevOpsslide wording
"A set of practices designed to help teams build, test, and release software faster and more reliably." It joins Development and Operations.
DevOps lifecycle
The repeating loop of phases, drawn as an infinity symbol: plan, code, build, test (Dev side), then release, deploy, operate, monitor (Ops side), feeding back into planning.
Event-drivenslide wording
DevOps automation runs in response to events: a code commit, a pull request to a special branch, automated testing, and passing tests automatically triggering the CI/CD pipeline.
Event / trigger
Something that happens (push, PR opened, tests passed, a schedule) and starts automation.
Pipelineslide wordinggeneral computer science meaning
"An architectural style for incrementally processing data with independent components or stages."
Pipeslide wording
A message queue between stages.
Filterslide wording
"A process, thread, or component that perpetually reads messages from an input pipe, one at a time, processes each message, then writes the result to an output pipe."
DevOps pipelineslide wording
Its goal is "to apply a series of checks, tests, and transformations onto a unit of change, such that a production environment is safely and reliably changed in a timely manner."
Unit of change
The thing that travels through the pipeline: a commit, a pull request, a build.
Pipeline stagesslide wording
Pre-Build (quick checks), Build (run build manager), Test (unit tests), Analysis (static analysis), Package (create image or bundle binaries), Staging (system tests in a staging environment), Deploy (transport the change into production), Post-Deploy (testing in production)."Each stage has a particular goal and function."
Hookslide wording
"A mechanism for specifying an action that occurs in response to an event." Commonly used to build pipelines.Examples: a git pre-commit hook running npm test; a webhook.
Federation of pipelines
There is no single global pipeline. Companies run hundreds to thousands of loosely aligned pipelines.
Environmentsslide wording
Development (Dev), Testing (Test / QA), Staging (Staging / UAT), Production (Prod). Others: Integration, Disaster Recovery (DR).
UAT
User Acceptance Testing: checking in a production-like environment that the release does what users need. Associated with the staging environment.
Provisioning
Creating and preparing machines or environments so they are ready to use (for example reserving and booting a fresh Ubuntu VM).
Toolchain
The set of tools linked together to take code to production (git, build tools, CI, configuration management, monitoring).
Serviceslide wording
A unit of software "exposed over a public and well-defined interface, i.e. a set of REST APIs". Each team is responsible for a separate service.
Microservicesslide wording
"An architectural style in which services are created as small and often stateless instances and connected through a central discovery service and property store." (Glossary 2)
Build / task managerslide wording
The tools a pipeline calls to do the real work: make, maven, grunt, npm, msbuild. "Pipelines are just integrative technology."
make: target and sourceslide wording
"A target refers to a group of commands. A source is a dependency for a target." Sources are used to infer which targets must run first.
Maven: phase, goal, pluginslide wording
"A phase is a stage in the build lifecycle. Each phase contains goals, which are executed by plugins." Phases: compile, test, package, verify, deploy.
grunt: taskslide wording
"A task executes a registered plugin or arbitrary javascript."
Build teamslide wording
A team that maintains CI scripts and infrastructure. They can serve as gatekeepers on code integration and help with build failures.
Spinnaker
Netflix's fully automated pipeline tool. Slide features: bake immutable VM images, built-in deployment strategies (highlander, red/black), restrict stages to time windows, Chaos Monkey integration.
Chaos Monkey
A tool that deliberately breaks things in production to test resilience. An example of shift-right testing.
CD smells / CD-Linter
Common misconfigurations in pipeline configuration files that violate CD principles, and a linter that detects four of them.

Continuous integration, delivery and deployment

Continuous Integration (CI)slide wording
"A practice where developers automatically build, test, and analyze a software change in response to every software change committed to the source repository."Earlier slide: frequently putting code changes together makes problems easier to identify. Smaller changes, easier debugging.
"Continuous" is imprecise
Lecture's caveat: code changes happen at discrete moments (diff time), and production updates happen at intervals.
CI principlesslide wording
Commit code frequently. Don't commit broken code. Fix broken builds immediately. Write automated developer tests. All tests and inspections must pass. Run private builds. Avoid getting broken code.
CI benefits (claimed)slide wording
Detect and fix defects faster; software health is measurable; fewer assumptions about the environment; less repetitive work; deployable software at any time; global feedback about failure gives confidence.
CI pain points
"Why did the build fail?" and builds that take too long.
Continuous Delivery
Every change is carried automatically through build, test and staging so it is always ready to release. The slides label the pipeline up to the staged, "pre-deploy" code this way.
Continuous Deploymentslide wording
"A process in which incremental software changes are automatically tested, vetted, and deployed to production environments." (Glossary 1)
Staging or bakingslide wording
"A stage in the deployment pipeline in which developers test a new software version in a production-like environment. For example, some companies might bake a new version for eight hours before deployment." (Glossary 1)
CI/CD
The two together: integrate and verify every change (CI), then carry it toward production (CD). Pronounced "see eye, see dee".

Roles, teams and organisation

Service Ownerslide wording
Outside coordination. Maintains and communicates the vision of the service.
Gatekeeperslide wording
Responsible for decisions to move to the next stage in the deployment pipeline. Decisions might be automated.
Release Engineer / Coordinatorslide wording
Responsible for the entire release process, including approving late-breaking additions, the back-out decision, and refereeing bug-severity disputes.
DevOps Engineerslide wording
Responsible for care and feeding of the tools used throughout the DevOps toolchain.
Reliability Engineerslide wording
Responsible for the time period immediately after deployment.
Two large pizzas ruleslide wording
"At Amazon, development teams should be no larger than what can be fed from two pizzas."It is about team size, not deployment time.
Silo
A team working in isolation with its own goals, tools and knowledge. Traditionally Dev and Ops are siloed.
Wall of confusionslide wording
The barrier between Dev and Ops. "Software goes over the wall. Ops owns provisioning and rollout."
Ticket system (pre-DevOps)slide wording
The interface between Dev and Ops: developers demanded deployments through tickets that operations handled manually. In theory this gives stability; in practice, long delays and silos that "blame each other for production problems".
Change ownershipslide wording
"A practice in which developers are responsible for software changes for all phases, including development, testing, deployment, and fixing problems." (Glossary 2)Summary slide: the developer has responsibility for the consequences of changes.
Change management
How an organisation controls the risk of changing production. In DevOps: changes are small, reviewed, automatically verified, exposed gradually, owned by their author, reversible, and learned from.
End-user communicationslide wording
"A practice enabling communication with users to receive feedback and gather requirements." (Glossary 2)

Computing environments and virtualization

Shell
A program that reads commands and runs them (sh, bash, PowerShell). /bin/sh is "the shell", a very old Unix program.
Why the command line?
Flexibility and remote access (cloud machines and devices have no screen), and understanding the computational context a program runs in.
Redirect
> writes a command's output to a file; >> appends to it.
Return code / exit code
The number a command returns when it ends. 0 means success; any other value means failure. Pipelines pass or fail on it.
Package manager
A tool that knows which pre-built packages exist and installs them: apk on Alpine, apt on Ubuntu, npm for Node.
Bit rotslide wording"does code rot?"
Code that has not changed stops working because its environment and dependencies change around it. "Often, the default experience is failure."
Computing environmentslide wording
"A unified view of code and configuration needed to operate and maintain its value": configuration + code, including dependencies, environment, ecosystem, stakeholders and users.
Ideal computing environmentslide wording
Reproducible, resilient, secure, scalable, flexible, maintains quality of service, good resource utilization.
"Software on your machine has no real value"
A program is worth nothing until it runs where users can reach it. Managing environments is hard, and programmers must be "end-user system admins".
Virtualization
Making one physical machine appear as several isolated machines or environments.
Virtual machine (VM)slide wording
"An efficient, isolated duplicate of the real machine." (Popek and Goldberg, 1974)
Host / hypervisorslide wording
The operating system running on the physical machine.
Guestslide wording
The operating system running in the virtual machine.
Virtual machine monitor (VMM)slide wording
Helps run the guest on the host. Implements the virtualization interface and enforces the illusion of isolated virtual machines.
Privileged instructionsslide wording
Operations only the kernel may run: I/O, memory address mapping, loading and reading system registers, changing processor mode between kernel and user.
Full emulationslide wordinghosted interpretation
Run the virtual machine as a user application, interpreting each instruction and emulating CPU, memory, disks and network. Examples: Bochs, video-game emulators.
Trap-and-emulate
Safe instructions run directly on the CPU; privileged ones trap to the VMM, which emulates them. Example: System/370.
Binary translation
Unsafe instructions are rewritten into safe calls before they run. Examples: QEMU, VMware, VirtualBox.
Hardware-assisted virtualizationslide wording
The CPU adds a guest mode and new instructions (VT-x) so VM operations are supported efficiently and the VMM is easier to implement. Examples: KVM, ESXi, Hyper-V.
Paravirtualizationslide wording
Patch the guest OS to enable virtualization through the VMM. Example: Xen.Trend: AWS moved from Xen to KVM.
OS-level virtualizationslide wording
"The operating system provides mechanisms for virtualizing resources. You are not performing full virtualization of a system." This is what containers use.
Headless
Without a graphical interface. Headless VMs, micro VMs and containers are infrastructure you "build, use, and throw away".
Classic VM
A fully loaded operating system with a graphical interface: optimized but heavyweight.
Bare metal
Running directly on physical hardware with no virtualization. Use: desktop, mobile, embedded, efficiency, CI harness.
Micro VM
A minimal, fast-starting VM. Use: embedded appliances such as Docker for Mac and WSL. Firecracker is still a foundation of AWS.

Containers (Workshop 1)

Container
An isolated process (or group of processes) with its own filesystem view, running on the host's kernel. A running instance of an image. Lightweight and disposable.
Image
A read-only, layered template of a filesystem from which containers are started. A "binary artifact".
Dockerfile
The text file of build instructions that produces an image.
Layer
The filesystem change made by one Dockerfile instruction. Each instruction line creates a new layer.
Build vs run
Building turns a Dockerfile into an image. Running starts a new container from an image.
RUN vs CMD
RUN executes a command while the image is being built and saves the result in a layer. CMD names the program a container starts when it runs.
Ephemeral
A container's own changes live only in that container. A new container starts from the unchanged image, so files and installed software from the previous one are gone.
Bind mountslide wording-v host_path:container_path
"A temporary connection between your local machine and the environment inside the container." Both paths refer to the same files, so data written there outlives the container.Host path on the left of the colon, container path on the right.
Registry
A server that stores images, such as Docker Hub, where FROM alpine:latest is pulled from.
Alpine Linux
A deliberately bare-bones Linux image. It has no Python, git or cloc until you install them with apk.
Interactive mode (-it)
Starts the container with an interactive terminal. Omit it when the container should just run its program and exit.
Docker vs Podmanslide wording
"Docker is closed source and is a commercial project, while podman is open-source." Same concepts.
latest vs pinned version
latest always gets the newest version but may break later. A pinned version is repeatable but ages. "There is no perfect answer here, only tradeoffs."

Environment variables and secrets (Workshop 2)

Environment variable
A name=value string in a process's environment, inherited from whatever started it. The standard way to pass configuration to a program without changing its code.
Terminal as a computational context
A terminal is a place where you can declare variables, like in a program. env lists them; export X=Y sets one; $X reads one.
Env file (--env-file)
A file of NAME=value lines used to set environment variables inside a container at run time.
Secret
Any value that controls access to a resource: token, password, private key. Tokens are a kind of secret.
Personal access token (PAT)slide wording
A secret that lets a user access the GitHub API and automate actions on GitHub from a program.
Principle of least privilegeslide wording
Grant only the least amount of privilege required to complete the task.Example: scope a PAT to one repo with an expiry date; open port 3306 only to VM1.
Baked-in secret
A secret written into a Dockerfile, image or source file. Anyone who can read the artifact can extract it. Never do this.
Secrets manager
A tool built to store secrets encrypted and hand them to programs at run time: GitHub repository secrets, podman secrets. Better than an env file, which is better than hard-coding.
Leaked credentials
A token committed to a repository. Attackers scan GitHub continuously and exploit leaks within minutes. Every workshop penalised it.

REST APIs

APIslide wordingApplication Programming Interface
The answer to "how can my software talk to other software?"
RESTslide wordingRepresentational State Transfer
A software architectural style from Roy Fielding's 2000 PhD thesis (chapter 5). REST APIs give clients an interface to back-end services, consume and produce JSON, and use HTTP requests such as GET, POST, PUT and DELETE.
HTTP verbsslide wording
GET retrieves, POST creates, PUT updates, DELETE deletes.
Resource
The noun in the URL. Collection /dogs, element /dogs/1234, association /owners/5678/dogs. States and attributes go after the ?.
REST constraintsslide wording
Client-server, stateless, cacheable, layered system, uniform interface.
Stateless
Each request carries everything the server needs; the server keeps no client session between requests.
Status codesslide wording
200 OK and 201 Created: it worked. 400 Bad Request: the client did something wrong. 500 Internal Server Error: the API did something wrong.
JSON
JavaScript Object Notation: a lightweight data format of objects (name/value pairs), arrays and values.
Hyrum's Lawslide wording
Cited under "do one thing well": once an API is public, "you can never remove it".
API design principles
Do one thing well; names matter; don't leak implementation details; minimise accessibility; don't make the client do what the API could do; version the API; paginate.

GitHub Actions (Workshop 3)

GitHub Actionsslide wording
GitHub's automation platform. Actions are event-driven and run commands that automate work on the code in your repo.
Workflowslide wording
A YAML file (.yml or .yaml) in .github/workflows/ that specifies what the automation does. "Workflows, when run, become actions."
on:slide wording
The required, critical key that names the events that trigger the workflow, such as push or pull_request.
Jobslide wording
One named task in a workflow. jobs: holds one or more.
Step / run:slide wording
steps: is the sequence of commands in a job. - run: is the prefix for a shell command.
runs-on:slide wording
Specifies what compute handles the job, for example self-hosted.
Action runnerslide wording
"Some compute that has been configured to perform GitHub actions."
Self-hosted vs GitHub-hosted runner
Self-hosted is your own machine (the workshop VM). GitHub-hosted is one of GitHub's headless VMs.
Contextslide wording
The variables GitHub provides to a workflow, such as github.actor and github.repository. Anything inside ${{ … }} accesses the context and is evaluated when the workflow runs.
Repository secret
A value stored encrypted in the repo's settings and read as ${{ secrets.NAME }}, so the token never appears in the workflow file.
YAML
A structured text format based on indentation. It converts one-to-one to and from JSON.
SSHsecure shell
An encrypted connection that gives you a terminal on a remote machine. Needs a username and a hostname or IP.

Configuration management and Ansible (Workshops 4 to 6)

Configuration managementslide wording
"A process in which an inventory of software and production assets is provisioned and controlled through package managers and tools such as Ansible."
Ansible
A configuration management tool, created by Michael DeHaan. Agentless, declarative and idempotent.
Infrastructure as Code (IaC)
Describing machines and their configuration in versioned files that tools apply automatically. In the matching example it pairs with Ansible.
Agentlessslide wording
"No ansible agents (software program) installed" on the machines being managed. The control node connects over SSH.
Agent
A program that would have to be installed and kept running on every managed machine. Ansible does not use one.
Control nodeslide wordingcontroller, Ansible workstation
"Any machine with Ansible installed." You run ansible or ansible-playbook from it. Any computer with Python can be one.
Managed nodeslide wordinghost, inventory
"The network devices (and/or servers) you manage with Ansible… Ansible is not installed on managed nodes."
Inventoryslide wordinghosts file
The list of managed nodes, optionally in groups such as [webservers]. "Inventory also known as hosts a.k.a. managed nodes."
Role of SSH
SSH is Ansible's transport: the encrypted channel the control node uses to reach each managed node and run tasks. It must be key-based and password-less so automation can run unattended.
SSH key pair
A private key that stays on the control node and a public key that is appended to ~/.ssh/authorized_keys on the managed node.
Playbook
A YAML file that lists plays. It describes the desired state of the hosts.
Play
One section of a playbook that maps a group of hosts (hosts:) to a list of tasks.
Task
One named step in a play that calls one module.
Module
The unit of work a task uses: apt, service, copy, template, uri, shell.
become
Privilege escalation: run the tasks as root, usually through sudo.
state:
The desired condition a module should ensure: present (installed), latest (installed and newest), started (running).
Declarativeslide wording
"Defines WHAT tasks should be accomplished." Defines only the logic; mutating variables is unusual. Derived paradigms: functional, logic."Ansible is declarative."
Imperativeslide wording
"Defines HOW tasks should be accomplished." Defines the control flow and state changes; mutating variables is very usual. Derived paradigms: procedural, object-oriented.
Idempotentslide wording
"When performing an operation again gives the same result." Running a playbook many times leaves the same end state.Slide analogy: looking at a cake is idempotent, eating a slice is not. GET, HEAD, PUT, DELETE are idempotent; POST and PATCH are not.
Handler
A task that runs once, later, only if a task that notifies it reported a change. Typically a service restart.
Template
A file with {{ variables }} that Ansible fills in before copying it to the host.
register / when
register saves a task's result in a variable; when runs a task only if a condition holds. Together: check, then act.
Orchestration
Coordinating configuration across several machines in a defined order, as in Workshop 6's database play followed by its app play.
Actions vs playbooksslide wording
Both are YAML, declarative and used in CI/CD. Actions automate the Git repo's lifecycle, are tied to Git events, run on a runner, and are not always idempotent. Playbooks automate configuration management and deployment, run from a control node, and are always idempotent.

Deploying and releasing

Deploy vs release
Deploying puts the code on production servers. Releasing makes the feature available to users. "Deployment is not releasing."
Feature flagsslide wordingtoggles, release toggles, feature flippers
"A mechanism for dynamically enabling features during production, often controlled by a global in-memory store and cached locally in service instances." (Glossary 1)"How deployed features become released features."
Anatomy of a feature flagslide wording
It has a unique name, has variations that an if uses to select a code path, and can have rules the evaluation engine uses to choose which variation to serve.
Stale feature flagsslide wording
A source of technical debt: flag management that leaves it ambiguous which flags are stale, and no developer incentive to clean up the code.
Dark launchingslide wording
"A practice in which code is incrementally deployed into production but remains invisible to users." (Glossary 1)"Deployed but not released." Enabled by feature flags.
Parallel run (Fowler)
A dark-launch variant: old and new code are both called and their results compared, but only one answer is returned to the interface.
Canary release
Release the new version to a small share of real users first (for example 5% or 10%), watch it, then widen. Usually done at the networking layer. Before: all v1. During: mostly v1, some v2. After: all v2.
A/B testing
Split users between variants (for example 50/50) and compare a metric such as conversion rate to see which is better. Done with feature flags or at the networking layer.
Blue-green deployment
Two complete environments. One is live; the new version is prepared on the other, then all traffic is switched. Uses separate delivery infrastructure.
Feature flags vs canaryslide wording
Flags: placed in the application; orchestrated by developers, product managers and QA; support rule-based and group-based targeting; rollback is granular to a specific feature. Canary: infrastructure networking layer; orchestrated by DevOps and SREs; rollback is the entire deployment.
Deflighting or rollbackslide wording
"A method for rolling back or decommissioning a defective change and removing it from the deployment pipeline." (Glossary 1)
Rollback optionsslide wording
1. Use the load balancer to shift traffic away from the canary release. 2. Disable the feature flag (application level, requires a push update or equivalent). "In any case, have a rollback plan."
Load balancing
Distributing incoming requests across several instances of a service. The routing layer that makes scaling, canary releases, blue-green switches and rollback possible.
Progressive delivery
The umbrella name used by the slides' source for gradual rollout methods: canary, feature flags, A/B tests, blue-green.
Every feature is an experimentslide wording
In continuous deployment a feature must demonstrate that it is useful: ROI, customer retention, engagement, conversion rates.
Cost of change (Boehm, 1981)slide wording
Relative cost to fix an error by when it is found: requirements 1, design 3–6, coding 10, development testing 15–40, acceptance testing 30–70, operation 40–100.Much less true under CI/CD; still true for airplanes, power plants, aircraft carriers.

Rings, blast radius and where testing happens

Deployment ringsslide wordingrollout rings
Concentric groups that receive a change in order: canaries, then early adopters, then users.
Canaries (ring 0)
The first, smallest group to get a change: internal users or volunteers. Most volatile; sees the most new features.
Early adopters
Users who opt in to get changes before general availability.
Blast radius
How much is affected if a change goes wrong: users, services, machines. It grows as a change moves to outer rings, so problems should be found in the inner ones.
Exposed feature set
The set of features switched on for a group. It is larger for early adopters and smaller and more stable for production users.
Shift-leftslide wording
Move testing earlier in the lifecycle (plan, design, dev). "Shift-left reduces cost of defects."
Shift-right
Extend testing later, into deploy, operate and measure: testing in production with canaries, monitoring, A/B tests and chaos experiments.
Telemetryslide wording
"A practice in which code is instrumented to compute metrics about feature use and software performance and stability." (Glossary 2)
Latency vs distribution
Report response time as a distribution (median, quartiles, tail), not one average. Workshop 6: 30 sequential requests per configuration.

Retrospectives

Retrospectivesslide wording
"A practice in which team members discuss the causes and consequences of an unexpected operation outage or deployment failure." (Glossary 2)
Three objectives of a retrospectiveslide wording
What worked (went well)? What didn't work? What can we do better?
Postmortem
A written retrospective after an incident: what happened, why, and what will change.
Hotwash
An immediate after-action review held right after an event. The README lists it as another name for a retrospective.
Why retrospectivesslide wording
Build trust, try new things, improve continuously, (self) reflection, collaborative learning, shared understanding.
Retrospective tipsslide wording
Vocabulary, ice breakers, foster team psychological safety, make it fun. Also: keep it simple, incorporate novelty, stay focused, make it action-oriented, bring in an outside perspective.
Psychological safety
People can say what really happened without fear of blame. Without it a retrospective cannot find the cause.
Meta-analysis of retrospectivesslide wording
With many retrospectives, developers can analyse them together "to uncover trends and systematic issues with deployment processes".

The ten adages of continuous deployment

1. Every feature is an experimentslide wording
Features must prove their value with data (A/B tests, telemetry) and can be removed.
2. The cost of change is deadslide wording
In continuously deployed systems, changing late is no longer far more expensive than changing early.
3. Be fast to deploy but slow (or slower) to releaseslide wording
Put code in production quickly; expose it to users carefully with flags, dark launches and canaries.
4. Invest for survival
Continuous deployment takes sustained investment in automation, tooling and infrastructure.Listed on the slide, not expanded in lecture.
5. You are the support personslide wording
Developers own their changes in production. Linked to change ownership and breaking down silos.
6. Configuration is codeslide wording
Configuration and infrastructure are versioned, reviewed and automated like source code. Linked to Ansible.
7. Comfort the customer with discomfortslide wording
"Releases are part of the user experience." Frequent change can unsettle users, so manage it: does the user choose, or not?
8. Looking back to move forwardslide wording
Learn from outages and failures through retrospectives.
9. Invite privacy and security in
Involve security and privacy early instead of at the end.Listed on the slide, not expanded in lecture.
10. Ready or not, here it comesslide wording
Continuous deployment is arriving whether or not teams are prepared. The slides' opening quote.
