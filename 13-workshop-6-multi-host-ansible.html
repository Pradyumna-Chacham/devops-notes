One host vs two

Single hostTwo hosts
LatencyLowest: no network between app and DBHigher: one extra hop per query
ScalingApp and DB compete for the same CPU and memoryEach tier can be sized and scaled on its own; several app servers can share one DB
Failure / blast radiusOne VM down takes everything downFailures are separable, but there are now more ways to fail (network, firewall, second VM)
SecurityDB listens only on localhostDB is exposed on the network, so binding, firewall and user host must be configured carefully
Configuration effortOne playTwo plays, ordering, cross-host variables

One playbook, two plays, two host groups

Inventory: two groups
[myserver]                # VM1, app server
<VM1-IP> ansible_user=<unityid>

[myserver1]               # VM2, database server
<VM2-IP> ansible_user=<unityid>
group_vars/all.yaml: shared by every host
db_name: pointsdb
db_user: appuser
app_dir: /opt/nearest-app
2-setup-config.yaml (condensed)
- name: Configure VM2 with mysql server
  hosts: myserver1                  # PLAY 1 → database host
  vars:
    db_client_host: "{{ hostvars[groups['myserver'][0]].inventory_hostname }}"
  tasks:
    - set_fact: { db_password_shared: "{{ db_password }}" }
    - apt: { name: mysql-server, state: present }
    - lineinfile: …bind-address = 0.0.0.0
      notify: restart mysql
    - …firewall, database, user, CSV import…

- name: Configure VM1 with Node.js app
  hosts: myserver                   # PLAY 2 → app host
  vars:
    db_host: "{{ hostvars[groups['myserver1'][0]].inventory_hostname }}"
  tasks:
    - …nodejs, npm, app files, systemd unit, verify…
  • A playbook is a list of plays. Each play maps one group of hosts to its tasks. This is what "orchestration" means here: one command configures different machines differently, in a defined order.
  • Order matters. The database play runs first so the database exists before the app starts and the final "verify the app" check can pass.
  • Hosts know about each other through the inventory: groups['myserver1'][0] is "the first host in group myserver1", and hostvars[…] reads another host's variables. Nothing is hard-coded, so re-provisioned VMs with new IPs only need an inventory edit.
  • The app code did not change. The systemd template now renders Environment=DB_HOST={{ db_host }} instead of 127.0.0.1. Same server.js, different environment variable: the README's "configure connection settings dynamically using Ansible environment variables or parameters".
Exam angleA likely short answer: "How did you point the app at the remote database without editing the app?" Through configuration injected at deploy time: an Ansible variable rendered into the service's environment (DB_HOST), which the program reads with process.env.

Opening the database to exactly one client

Three things had to change on VM2 before VM1 could connect. Each is a declared piece of configuration, and each is scoped to VM1's address, not to the world (least privilege again).

LayerDefaultWhat the playbook sets
MySQL bind address127.0.0.1: local connections onlylineinfile sets bind-address = 0.0.0.0, then a handler restarts MySQL
FirewallVCL images reject inbound traffic on unlisted portsAllow TCP 3306 only from VM1's IP
Database user'appuser'@'localhost''appuser'@'<VM1 address>' with GRANT SELECT only
- name: Bind MySQL to all interfaces
  lineinfile:                       # ensure one line of a file has this content (idempotent)
    path: /etc/mysql/mysql.conf.d/mysqld.cnf
    regexp: '^bind-address'
    line: 'bind-address = 0.0.0.0'
  notify: restart mysql
- meta: flush_handlers              # restart now, because later tasks need the new setting

Benchmarking: collecting the data

The requirement: issue 30 sequential HTTP requests to each configuration and record each request's duration in milliseconds plus the total elapsed time.

function benchmark(url, n = 30):
    samples = []
    run_start = now()
    for i in 1..n:                        # sequential: one finishes before the next starts
        t0 = now()
        response = HTTP GET url           # includes connect + server work + full read
        samples.append((now() - t0) in ms)
    total_elapsed = (now() - run_start) in ms
    return samples, total_elapsed, mean / median / min / max / p95 of samples

results1 = benchmark("http://<config-1-host>/")
results2 = benchmark("http://<config-2-host>/")
write CSV: config, request number, duration_ms, status
  • Sequential requests measure per-request latency. They say nothing about behaviour under concurrent load (throughput).
  • Total elapsed is measured around the whole loop, so it is slightly more than the sum of the durations.
  • Report a distribution, not one number. The mean hides outliers; the median and a high percentile (p95) describe typical and worst-case experience. That is why the deliverable was a histogram or box plot.
  • Use a monotonic high-resolution clock (time.perf_counter() in Python) and keep everything else equal between the two runs.
This is telemetry in miniature. Glossary 2 defines telemetry as "a practice in which code is instrumented to compute metrics about feature use and software performance and stability". Decisions about architecture should rest on measurements like these.

Reading it: the whole distribution shifts right by roughly 8 to 12 ms. The typical request is about 11% slower with the database on another VM (mean 80.4 → 89.5 ms), which is the cost of the extra network round trip. The tails are about the same (max 117 vs 116 ms), so the slowest requests are dominated by something other than the DB hop. With 30 samples and a standard deviation near 10 ms, treat the size of the gap as approximate, but the direction is consistent across min, quartiles, median and mean.

The trade: you pay about 10 ms per request and extra configuration to get tiers that scale and fail independently. Whether that is worth it is a judgment about the system, and the measurement is what lets you make it.

Practice

The exam has three question types: true / false with corrections, matching concepts, and naming the tool from a code snippet. "Self-check" and "Read the code" items are for understanding only. On true / false, underline the wrong word and write the fix; a plain "not" earns nothing.
True / FalseIn an Ansible playbook, each play targets a group of hosts, and one playbook may contain several plays.
True. WS6 used one play for the database host and one for the app host.
True / FalseMoving the database to a second VM reduced the median response time in the workshop.
False. It increased it (about 77.6 → 88.2 ms in your data) because each query now crosses the network.
Read the codedb_host: "{{ hostvars[groups['myserver1'][0]].inventory_hostname }}" What does this expression evaluate to, and why write it this way?
The address of the first host in the inventory group myserver1 (the database VM). The value comes from the inventory, so if the VMs are re-provisioned with new IPs you edit only the hosts file, not the playbook or the app.
Read the codeA benchmark script measures total_elapsed around the whole loop and also sums the 30 durations. Which is larger and why?
total_elapsed, slightly, because it also includes the script's own overhead between requests (loop bookkeeping, recording the sample). In your run: 2,415 ms total vs 2,411 ms summed for Config 1.
Self-checkWhy does the database play come before the app play in the playbook?
The app depends on the database. Running the DB play first means the database, user, firewall rule and data exist before the app service starts, so the playbook's final check that the app responds can succeed in a single run.
Self-checkGive two reasons to separate an app server and a database server despite the added latency.
Independent scaling and sizing of each tier (several app servers can share one database); fault and resource isolation, so a busy or crashed app does not starve or take down the database; tighter security boundaries per machine.
Self-checkWhy report a box plot or histogram instead of just the average response time?
An average hides spread and outliers. Two systems with the same mean can have very different worst cases. The median, quartiles and tail show what a typical request and a bad request look like.
