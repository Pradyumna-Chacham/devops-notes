Pull requests, Modern Code Review, and diff time

Pull request (PR)
A request to merge one branch into another. It can contain one or more commits, shows the diff, hosts discussion, and is where automated checks report.
Diff time
The critical moment in the process when a code change is proposed. It is when peer review happens and, increasingly, when static analysis runs ("Scaling static analyses at Facebook", 2019).
Modern Code Review
Lightweight, tool-based, asynchronous peer review of a diff before merge, as opposed to formal inspection meetings ("Modern code review: a case study at Google", 2018).
Continuous Integration (CI)
Frequently putting everyone's changes together. Smaller changes are easier to debug. Aim for the "Goldilocks" granularity: not too big, not too small.

Workshop 2 also asked for two professional habits: meaningful commit messages and developing through pull requests even when working alone.

Roles and team size

RoleResponsible for
Service OwnerOutside coordination. Maintains and communicates the vision of the service
GatekeeperDecisions to move to the next stage in the deployment pipeline (decisions might be automated)
Release Engineer / CoordinatorThe entire release process: approving late-breaking additions, the back-out decision, refereeing bug-severity disputes
DevOps EngineerCare and feeding of the tools used throughout the DevOps toolchain
Reliability EngineerThe time period immediately after deployment

The "two large pizzas" rule (Amazon): a development team should be no larger than what two pizzas can feed. It is about team size, and small teams each own one service, exposed over a well-defined interface such as REST APIs. Many independent services make a microservices architecture. Lamport's warning comes with it: "A distributed system is one in which the failure of a computer you didn't even know existed can render your own computer unusable."

Two terms defined in the same lecture: provisioning (creating and preparing machines or environments) and toolchain (the set of tools chained together to move code to production).

REST APIs

An API answers "how can my software talk to other software?". REST (Representational State Transfer, Roy Fielding's 2000 thesis) is an architectural style: resources are nouns in the URL, HTTP verbs are the operations, and data travels as JSON.

VerbActionExampleIdempotent?
GETReadGET /repos/{owner}/{repo}/branches lists branchesYes (and safe)
POSTCreatePOST /repos/{owner}/{repo}/git/refs creates a branchNo
PUTUpdate / replacePUT /recipes/3Yes
DELETEDeleteDELETE /recipes/1Yes

Status codes

  • 200 OK, 201 Created: it worked
  • 4xx the client did something wrong: 400 bad request, 401 bad credentials, 404 not found, 422 validation failed (branch already exists)
  • 500 the server did something wrong

Constraints and design rules

  • Client-server, stateless, cacheable, layered, uniform interface
  • Collections /dogs, elements /dogs/1234, associations /owners/5678/dogs
  • Filters go after the ?: /dogs?color=red
  • Version the API; paginate; use standard auth (OAuth)
Test your token from a shell
curl -H "Authorization: Bearer $CSC_519_GITHUB_TOKEN" https://api.github.com/users/UNITY_ID_ncstate
# -H adds a request header. Success returns JSON; an expired token returns "Bad credentials".
API design principles quoted in lecture: do one thing well; you can never remove a public API (Hyrum's Law); names matter; don't leak implementation details; don't make the client do what the API could do.

Activity prompt and a model answer

Self-checkWhat could go wrong in a DevOps pipeline?
Tests that are missing, weak or flaky let a bad change through, or block good ones. A broken build stops the whole team. Staging differs from production, so something passes there and fails live. Secrets leak into the repo, logs or images. The pipeline is slow, so people bypass it. A bad deploy has no rollback plan. The pipeline's own configuration is wrong. And an automated path to production is itself a target, so its credentials need least privilege.

Check yourself

Self-checkWhy does lecture call "continuous" imprecise for both CI and CD?
Code changes arrive at discrete moments (diff time), and updates to production happen at intervals. Neither is literally continuous.
Self-checkName the stages of the example pipeline on slide 16 in order.
Code → Testing → Build Release → User Acceptance Testing → Staged code ("pre-deploy") → Production.
Self-checkWhich role decides whether to back out a release, and which role watches the system right after deployment?
The Release Engineer / Coordinator makes the back-out decision. The Reliability Engineer is responsible for the period immediately after deployment.

Practice

The exam has three question types: true / false with corrections, matching concepts, and naming the tool from a code snippet. "Self-check" and "Read the code" items are for understanding only. On true / false, underline the wrong word and write the fix; a plain "not" earns nothing.
True / False"Diff time" is the moment when code review and, increasingly, static analysis happen.
True. It is a discrete event in the process, typically the pull request.
True / FalseREST APIs typically consume and produce XML and use the verbs OPEN, READ, WRITE, CLOSE.
False. They typically use JSON and the HTTP verbs GET, POST, PUT, DELETE.
True / FalseAn HTTP 500 status code means the client sent a bad request.
False. Change 500 to 400 (or: 500 means the server failed).
Self-checkIn one sentence each, define pull request and Modern Code Review.
A pull request proposes merging one branch into another and is where the diff is discussed and checked. Modern Code Review is lightweight, tool-supported peer review of that diff before it merges.
True / FalseThe "two large pizzas" rule states that a DevOps pipeline should take less time to deploy than it takes for the team to eat two large pizzas.
False. Sample question from the slides. The rule is about team size: a team should be no larger than two large pizzas can feed.
True / FalseThe Gatekeeper is responsible for the time period immediately after deployment.
False. Change Gatekeeper to Reliability Engineer. The Gatekeeper decides whether a change moves to the next pipeline stage.
MatchingConnect each role to its responsibility: Service Owner · Gatekeeper · Release Engineer · DevOps Engineer · Reliability Engineer.
Service Owner: outside coordination and the vision of the service. Gatekeeper: decisions to move to the next pipeline stage. Release Engineer: the entire release process, including back-out decisions. DevOps Engineer: care and feeding of the toolchain. Reliability Engineer: the period immediately after deployment.
